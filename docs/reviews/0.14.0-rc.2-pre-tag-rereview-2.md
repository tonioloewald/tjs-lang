## Blockers

### B1. The capabilities shadow rebinds `this` and breaks class-instance capabilities (correctness, confirmed; filed as major, treated as blocking)
`src/vm/vm.ts:332`. `Object.create(admitted.capabilities)` makes the shadow the receiver for every inherited getter and method. Both failures below were reproduced at HEAD:
- `class Caps { #s = {...}; get store() { return this.#s } }` makes vm.run **throw** a raw `TypeError: Cannot access invalid private field`. The throw comes from `if (!capabilities.store)` at vm.ts:340, so the caller gets an exception, not a monadic error.
- `class Caps { #n; async fetch() { return this.#n } }` makes every httpFetch return the AgentError `Cannot access invalid private field`. WeakMap-keyed-by-`this` state fails the same way.

Both shapes worked before rc.2. Two claims are now false for this shape: CHANGELOG.md:146 ("works as before") and the vm.ts comment ("Reads fall through to the host object as before rc.2"). The new test covers only a getter that does not read `this`.

**Fix direction:** keep the host object as the receiver. Options:
- A Proxy whose `get` does `Reflect.get(host, k, host)` and serves `store` from the run-local default only when the host has none.
- Leave `ctx.capabilities` as the host object and have the store atoms read `ctx.capabilities.store ?? ctx.defaultStore`.

Read `store` presence once, inside try/catch, and turn a failure into a monadic error. Add repro rows for a `#private`-backed getter and method. Fold in U2 below (refuse a non-object `capabilities` by name).

**Re-review scope:** correctness plus blast-radius over the remediation diff. The security lens should confirm the VM still never writes to the host object (the guest-key-writes allowlist entry).

**Cycle note:** this is the third remediation of the capabilities copy:
1. Round 20: shallow copy.
2. Round 21 BLOCK: the copy dropped prototype members.
3. Now: the shadow keeps the members but loses the receiver.

Each patch repaired one property of the host object and broke another. The underlying question is whether the VM should copy or wrap the host's capabilities object at all, rather than keep it and hold the run-local default store separately. Plan that before patching again.

## Plan (round 22, filed before acting)

**Underlying problem (B1):** three rounds copied or wrapped the host's capabilities object, and each
broke a different property of it: own-only members, then the prototype, then the receiver. The VM
touched the object only to attach a default store.

**Fix: do not copy or wrap it.**
- `ctx.capabilities` is the host object exactly as passed. The VM never writes to it, and never
  reads `store` up front (a getter that throws is read inside an atom, where failures are monadic).
- The run's default store lives on the run, as `ctx.defaultStore`. Only the store atoms read
  `ctx.capabilities.store ?? ctx.defaultStore`, and they are listed by a grep for
  `capabilities.store`.
- A non-object `capabilities` is refused by name in admission.
- Rows: a `#private`-backed getter and a `#private` method `fetch` work; a getter that throws gives
  a monadic error; the host object stays untouched; and the existing rows still pass (no sharing
  between runs, a frozen object, nested `agentRun`).

**Fetch minors (same round, bounded):**
- A method allowlist (GET, HEAD, POST, PUT, PATCH, DELETE, OPTIONS), refused otherwise, on both
  paths.
- The routing headers join the refused set: `forwarded`, `x-forwarded-*`, `x-original-url`,
  `x-rewrite-url`, `x-http-method-override`. The comment is corrected to "routing and framing
  headers plus the VM's own"; `Cookie`, `Origin` and `Referer` stay allowed on purpose (APIs use
  them, and the browser controls the real ones).
- `credentials: 'omit'` on the default path: ambient browser authority is not a capability.
- A cross-origin 307/308 is refused (it would carry the guest's body to another origin).
- An opaque-redirect row with a stubbed `fetch`, which also asserts the body is cancelled.
