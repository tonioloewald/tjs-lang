## Blockers

### B1 — Emitted `Enum`/`Union`/`Exactly`/`FunctionPredicate` are NOT callable, while the real runtime's now are
`src/lang/emitters/js.ts:2062,2076,2081,2089` · lens: correctness · **verified**

`asPredicate` wraps Type, Union, Enum and FunctionPredicate in `src/types/Type.ts`, but in the inline stub only `Type` is wrapped in `__pred` (js.ts:2032) — confirmed by inspection during triage. Emitted `typeof Age === 'function'` but `typeof Colour === 'object'`, and `Colour('red')` throws `TypeError: out.Colour is not a function`; the same declaration via the library `Enum` returns `true`.

Two compounding problems:
1. `CHANGELOG.md` 0.14.0 states *"The inline stub emits callables too, so emitted code and the real runtime agree on shape as well as on decisions"* — false for four of five forms.
2. It names `src/lang/predicate-callable.test.ts` as the pin, but that file's EMITTED block transpiles only `Type Age 0`; Enum/Union/FunctionPredicate callability is asserted **only against the real runtime**. The guard is green exactly where the drift is, and cannot go red.

**Fix:** wrap the remaining stub constructors in `__pred` and drive the EMITTED and real-runtime describe blocks from **one shared CASES table**, so a form added to one side must appear on the other. If the narrow scope is deliberate instead, correct the CHANGELOG sentence and record the asymmetry in `docs/type-identity.md`.
**Re-review scope:** if the stub changes — correctness + blast-radius over the remediation diff (emitted-runtime parity, `rt-namespace.test.ts` allowlist, `type-identity.test.ts`, inline-runtime size). If only docs change — Tier 0.

### B2 — `Predicate` is not exported from any package entry point
`src/types/index.ts:44` · lens: blast-radius · **verified**

`src/types/Type.ts:85` re-exports `Predicate`, but `src/types/index.ts` uses an explicit named list that omits it (confirmed by triage: grep for `Predicate` in that file returns only `FunctionPredicate*`). `src/index.ts` does `export * from './types'`, so the brand never reaches the barrel — and there is no wildcard subpath in `exports`, so no deep-import escape hatch exists. Verified absent from `tjs-lang`, `tjs-lang/css`, `tjs-lang/lang`, `tjs-lang/runtime` under **both** the `bun` (source) and `default` (dist) conditions.

`CHANGELOG.md` line 43 (`Age instanceof Predicate // true`) and line 81 (*"`isColor instanceof Predicate` is `true`"*) are consumer-facing examples that cannot be written. A static `import { Predicate } from 'tjs-lang'` fails hard — `SyntaxError: Export named 'Predicate' not found` — taking the consumer's whole module graph down. The only site where the identifier resolves is `src/lang/predicate-callable.test.ts:24`, which imports it from `'../types/Type'` — i.e. the guard can see it precisely because it bypasses the published surface.

**Fix:** add `Predicate` to the named re-export in `src/types/index.ts`, and change `predicate-callable.test.ts` to import it from the **public** entry so this would have failed. Assert against `dist/index.js` and `dist/tjs-css.js`, not source, since that is where it failed.

**Entangled constraint from the refuted duplication finding — do not fix B2 in isolation.** The skeptic confirmed six independent `class Predicate` declarations across bundles (`index.js`, `tjs-css.js`, `tjs-lang.js`, `tjs-browser.js`, `tjs-runtime.js`, `tjs-schema.js`), so `Object.getPrototypeOf(css.isColor) !== Object.getPrototypeOf(main.Type('Age',0))` today. That is currently harmless **only because nothing can import the brand**. The moment `Predicate` is exported, `docs/runtime-fusion.md`'s "code fuses, data unions" rule applies and a shape-versioned global slot (the `MonadicError` treatment) becomes mandatory — with a **bundle-level**, not source-level, test. Ship both changes together.

### B3 — The documented hard pre-tag gate is RED
`src/lang/dogfood-tests.test.ts:676` · lens: gate/coverage · **observed in triage**

CLAUDE.md makes a plain `bun test` with nothing skipped a hard, hook-enforced pre-tag gate. I ran it:

```
4960 pass  7 skip  1 fail   Ran 4968 tests across 240 files. [231.62s]   exit=1
(fail) dogfood: our own test suites survive conversion > converts, runs, and preserves every assertion
  expect(rate.tests).toBeGreaterThanOrEqual(BASELINE.testRate)  Expected: >= 1  Received: 0.9997738068310337
  BROKEN BY SUITE:  1  .dogfood-sQdx7l/repo-hygiene.test.ts
```

Run **in isolation** (`bun run test:dogfood`) it passes: exit 0, *"0 assertions lost, 0 tests broken, 0 suites that will not convert."* So the ratchet is **order/environment dependent**, not deterministically broken. The likely mechanism is that `src/repo-hygiene.test.ts` shells out to `git` and `npm pack --dry-run` against `ROOT = import.meta.dir/..`, so the converted copy running from a `.dogfood-XXXX/` scratch tree inspects a different (and concurrently-mutating) repo state than the original.

This is **not** dismissible as pre-existing or unrelated: no tag may be pushed while the gate is red, and a ratchet that reports differently depending on what else is running is a ratchet nobody can trust. Either exclude `repo-hygiene.test.ts` from the dogfood corpus **with a written reason** (it is a test *about the repo*, not about the language — converting it measures nothing), or make its `ROOT` resolution refuse to run outside the real repo.

Separately observed, and flagged rather than waved away: one `test:fast` invocation out of five returned **4935 pass / 1 fail / 35 skip** (vs 4939/0/32 on the other four), against a log line showing `live LLM failed after retries (LLM Error: 400 - transient)`. Consistent with CLAUDE.md's *"a cold server fails the first run on model load"*, but the failing test name was not captured. Worth confirming the 3 extra skips + 1 fail are entirely LM-Studio-health-driven before trusting a green `test:fast` as evidence.

**STATUS: RESOLVED** — 2026-09-24. Took the first option: `repo-hygiene.test.ts` is excluded from the dogfood corpus with the reason written into `SKIP` in `src/lang/dogfood-tests.test.ts`. The mechanism the review suspected is right and checkable: after the `import.meta` rewrite the converted copy's `ROOT` still resolves to the real repo, so it measures live repo state rather than conversion. This session produced a direct instance — a `make` that failed on lint left `dist/` absent, and `repo-hygiene`'s *"every directory named in `files` contributes something"* went red on exactly that. A ratchet whose verdict depends on whether `dist/` exists at that instant is measuring the build, not the language.

**The gate is green:** plain `bun test`, live LM Studio up, nothing skipped by choice — **4995 pass / 7 skip / 0 fail**, 5002 tests across 243 files, exit 0. The 7 skips are self-skips (vision and similar), as CLAUDE.md describes. `test:dogfood` in isolation: *0 assertions lost, 0 tests broken, 0 suites that will not convert*.

The separate `test:fast` 4935/1/35 observation is **not** closed by this — the failing test name was never captured, so there is nothing to confirm or refute. It stays in `TODO.md` as a named follow-up rather than being declared explained.

## Majors (non-blocking — file before or with the release)

### M1 — Emitted runtime types no longer serialise: `JSON.stringify(EmittedType)` → `undefined`
`src/lang/emitters/js.ts:2025` · correctness · **verified**

Before this diff the emitted `Type('Age',0)` was a plain object and stringified to `{"description":"Age","__runtimeType":true,"default":0,"__ex":0}`. After, it is a function: `JSON.stringify(Age)` → `undefined` and `JSON.stringify({f: Age})` → `{}` — **the key silently vanishes, no error**. `asPredicate` adds a `toJSON` in `src/types/Type.ts` precisely to close this, and `src/types/predicate-brand.ts` documents it as *"a quiet data-loss break … no error, just a missing value somewhere downstream"*. The `__pred` stub has no `toJSON` (`grep toJSON src/lang/emitters/js.ts` → eight hits, all `toJSONSchema`). CHANGELOG advertises "Runtime types now serialise" without qualifying it as library-only.

**Fix:** add `toJSON` to `__pred` (skip `check`/`toJSON`/`schema` and function-valued own properties, same rule as `asPredicate`); add a serialisation case to the EMITTED block asserting stub and real runtime produce identical JSON for `Type('Age', 0)`.

**STATUS: RESOLVED** — fixed 2026-09-24. `toJSON` added to `__pred` with the exclusion rule as prescribed, and serialisation cases added to the EMITTED block, driven by the same shared `FORMS` table as the rest of it so a new form must pass on both sides.

**One part of the prescription could not be followed as written, and the reason is itself a finding.** Stub and real do *not* produce identical JSON for `Type('Age', 0)`, and cannot without a separate change: the stub names the witness `__ex` where the real runtime says `example`. So the assertion is the stronger available one — the emitted output is byte-identical to **the pre-0.14.0 emitted shape** the finding itself quotes, proving this restored behaviour rather than inventing a plausible-looking format. Where both sides do share field names (`Enum`), identical-JSON *is* asserted. The `__ex`/`example` divergence is now pinned in both directions by `predicate-callable.test.ts`, recorded in `docs/type-identity.md` under a new "Surface, not decisions" heading (that page's disagreement list was about verdicts only, which is why a naming divergence had nowhere to live), and tracked in `TODO.md` — unifying them changes the serialised shape of every emitted type, so it is a deliberate change, not a drive-by.

The CHANGELOG claim the finding called unqualified is now qualified in place: it states the emitted path explicitly, and says why the distinction matters — the stub always wins in emitted code, so a `toJSON` in the library only is a fix the shipped semantics never received.

### M2 — `compilePredicate` brands every cluster export, including multi-argument ones
`src/lang/predicate.ts:757` · correctness · **verified**

`src/css/index.ts:196` goes out of its way *not* to brand `isStyleValueFor` ("a BINARY relation… branding it would make `instanceof Predicate` mean 'callable and boolean-ish'"), with a test at `predicate-callable.test.ts:162`. But `compilePredicate` — public API, and the function that *produces* the underlying `isStyleValueFor` — brands every name in `exportNames` unconditionally. The same diff widened `src/lang/runtime.ts:1488` to accept functions, so a branded binary relation now takes the RuntimeType branch and is called with **one** argument. Measured: `checkType('red', isOneOf)` → null, `checkType('blue', isOneOf)` → null, `checkType(12345, isOneOf)` → null. A validator that always says yes, with no diagnostic. The brand also *erases* arity (`isOneOf.length === 0`), removing the one defence a careful consumer had. The repo's own `isStyleValueFor` fails **closed** instead — both directions are a confident wrong answer.

One rule, two addresses, already drifted at birth. **Fix:** apply the arity rule where the brand is attached (`brandPredicate` refuses/skips arity > 1, or `compilePredicate` brands only `fn.length <= 1`), move the carve-out comment from `src/css/index.ts` to `predicate-brand.ts` so the rule lives with its enforcement, and add a case asserting a binary cluster member is unbranded.

**STATUS: RESOLVED** — fixed 2026-09-24, taking the first option so the rule has exactly one address: `brandPredicate` declines `fn.length > 1` and returns the function **untouched** (not half-branded), so `compilePredicate` brands what qualifies without restating the test — restating it is how these two drifted in the first place. The carve-out comment moved to `predicate-brand.ts`; `src/css/index.ts` now points at it.

The finding's arity observation turned out to be load-bearing rather than incidental: the rest-args fuel wrapper reported `length === 0`, so the rule had **no input to read**. `compilePredicate` now copies the underlying `length` and `name` onto the wrapper first — `name` because a declined relation still needs a usable stack trace. Arity `0` is branded deliberately: `(...args) => …` and `() => …` both report it, so zero means *unknown*, not *not a predicate*, and refusing it would break legitimate predicates to catch a shape arity cannot distinguish.

Reproduced before fixing, per the repo's bug-fix rule — `src/lang/predicate-arity.test.ts` went red on four cases and now covers all three directions the miscall can take (always-yes as measured here, fails-closed, and throws), plus a sweep asserting no binary export anywhere in `tjs-lang/css` carries the brand, with an apparatus check that a binary export exists at all.

### M3 — The AST format-version gate is consulted only in `AgentVM.run()`
`src/vm/runtime.ts:3956` / `:4003` / `:4565` · security (merged with a duplicate correctness finding) · **verified**

Confirmed in triage: `astVersionProblem` has **exactly one** non-test call site, `src/vm/vm.ts:257`. `agentRun`'s token branch and its inline-AST branch both call `seqAtom.exec(...)` directly; `storeProcedure` validates only `.op` and JSON size. Demonstrated: `vm.run({$ajs:99, op:'seq', steps:[{op:'storeSet',key:'pwned',value:'yes'},…]})` is refused, while the byte-identical AST reached via `{op:'agentRun', agentId: <that AST>}` executes its full body — the `storeSet` fired, `error` was null. Both branches also run **before** the `agent.run` capability check, so no capability is required. Guest code can likewise persist an unreadable-format AST via `storeProcedure` and invoke it by token.

Latent in 0.14.0 (`AST_VERSION === 1`), but the whole stated reason for landing the field now is that *today's* builds are the readers that must refuse tomorrow's v2 — and `src/vm/ast-version.ts`'s own docstring names `procedureStore` as the motivating case. Builds shipped with this hole cannot be retroactively patched.

**Fix:** call `astVersionProblem` at every point an AST enters execution or storage — both `agentRun` branches (as an `AgentError`, staying monadic) and `storeProcedure` (refuse at write time). Extend `src/vm/ast-version.test.ts`, every case of which currently goes through `run()`.

**STATUS: RESOLVED** — fixed 2026-09-24, as the general case rather than the two call sites. `checkAstVersion(ast, where)` is now the one gate; `AgentVM.run`, `resolveProcedureToken` and `storeProcedure` all go through it, and `vm.ts` was moved off its direct `astVersionProblem` call (one gate must not quietly become two). `storeProcedure` refuses at **write** time, per the finding. `src/vm/ast-version-boundaries.test.ts` makes the boundary set enumerable three ways — behavioural drive-through per boundary with an apparatus check, structural brace-matched body scan, and a generalised sweep that flags **any** other `procedureStore` reader that is ungated. Mutation-tested: removing any one gate turns it red.

### M4 — Builder-produced ASTs carry no `$ajs`
`src/builder.ts:528` · correctness / blast-radius (merged) · **verified**

Confirmed: `AST_VERSION_KEY` has exactly one writer, `src/lang/emitters/ast.ts:336`. `TypedBuilder.toJSON()` returns a bare `{ op: 'seq', steps }` — `Agent.take({name:''}).return({name:''}).toJSON()` → keys `["op","steps"]`, and `vm.run` accepts it. The Builder is a main-entry export (`src/index.ts:23`), exposed as `vm.Agent`, documented in CLAUDE.md's Core APIs and `DOCS-AJS.md`, and the repo's own `src/use-cases/client-server.test.ts:64` serialises `logic.toJSON()` over HTTP and into `storeProcedure`.

So `src/vm/ast-version.ts`'s *"New ones always carry the field… the population of unversioned ASTs stops growing"* and the CHANGELOG's *"turning an unbounded set into a finite, shrinking one"* are both false as written, and `ast-version.test.ts` cannot see it because every case goes through `transpile()`. Worse than merely unversioned: once `AST_VERSION` becomes 2, builder-emitted v2-shaped ASTs will report as v1 and be **executed under v1 semantics** rather than refused.

**Fix:** stamp the version as the first key in `TypedBuilder.toJSON()`, and add a **producer-sweep** assertion — every public path yielding a runnable AST carries the field — so a third producer fails by name. If exclusion is deliberate, say so in `ast-version.ts` and correct both claims.

**STATUS: RESOLVED** — fixed 2026-09-24, exactly as prescribed. The version is the first key of `TypedBuilder.toJSON()`, at the **root only**: nested branches splice `.steps` rather than re-serialising, so an inner `seq` never carries a field that describes nothing there (asserted). `src/vm/ast-version-producers.test.ts` is the producer sweep — both producers asserted behaviourally, plus a scan that fails by name on any file constructing a `seq` root without the stamp, with `vm/runtime.ts` exempt **with a written reason** (synthetic nodes handed straight to `seq.exec`, never persisted, never crossing a boundary). The finding's "worse than merely unversioned" case — builder v2 ASTs executing under v1 semantics — is what the sweep exists to prevent recurring. One detail the review did not name and the fix turns on: the assertion must be `'$ajs' in ast`, **not** `astVersionOf(ast) === AST_VERSION`, since absent reads back as the legacy default (1) and so the obvious check passes for precisely the ASTs it is meant to catch. The two claims the finding called false as written are now true; both were also left standing in place and annotated rather than quietly reworded.

### → `UPSTREAM.md` + a GitHub issue on **`tosijs-ui`**
