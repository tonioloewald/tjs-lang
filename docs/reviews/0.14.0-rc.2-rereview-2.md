## Blockers

### B1. A block `let` (or an atom `result`) that shadows an outer `const` is rejected (correctness, confirmed)
- **Where:** `src/vm/runtime.ts:3343` (`isConstBinding`), called from varSet and from exec's result binding (about line 2960).
- **What happens:** `function f(){ const x = 1; let out=[]; for (const i of [1,2]) { let x = i*10; out.push(x) } return {out,x} }` returns `{"$error":true,"message":"Cannot reassign const variable 'x'","op":"varSet"}`. The JavaScript is legal. The const check walks the scope chain (`constAt(ownerOf(ctx,key),key)`), but a declaration writes `ctx.state`. The new docstring says "the check and the assignment can never disagree"; that holds for varAssign and is false for varSet and for the result binding. `constSet` already fixed this for block `const` (M-1), so its two siblings have drifted from it. The failure violates the subset invariant: legal source is rejected.
- **Not a regression:** reproduced at 554799d and before e4dbb41 as well.
- **Fix:** split by intent. Assignment (varAssign, and exec with `resultAssign`) checks `constAt(ownerOf(ctx,key),key)`. Declaration (varSet, and exec without `resultAssign`) checks `constAt(ctx.state,key)`, the current scope only, as constSet does. Add test rows for block `let` shadowing an outer const, through varSet and through an atom result.
- **Re-review scope:** correctness, over the remediation diff.

### B2. A transpiled `arr.push(x)` statement is never heap-accounted (correctness + security budget, confirmed)
- **Where:** `src/vm/runtime.ts:3875` (`push` atom). Also `src/vm/heap-scope.test.ts` and `src/vm/cost-invariant.test.ts`.
- **What happens:** with `maxHeapBytes: 1_000_000`, `let arr=[]; let s='x'.repeat(1000); let i=0; while(i<20000){ arr.push(s+i); i=i+1 }` returns `{len:20000}` and no error, holding about 20MB live. The transpiler emits `{op:'push', list: ident('arr'), item}` with no `result`. `push` mutates the list in place, nothing is rebound, and `trackHeapWrite` never runs. The heap tests build `push` with `result: 'list'`, which the transpiler never emits, so they guard a path that does not ship. That is the "green that cannot go red" pattern from `docs/postmortem-ts-emitter.md`.
- **Not a regression:** same at 554799d and before e4dbb41. It is still a live hole in the space budget on the recommended path for untrusted code.
- **Fix:** account for in-place growth inside `push` itself, by charging the appended item to the ledger entry of the binding that owns the list. Alternatively, have the emitter bind the result. Then audit sibling in-place mutators (`unshift`, `splice`, the Object.assign-like atoms, `obj[k]=` member writes) for the same gap. Rewrite the heap push test so it runs `transpile(...)` output and measures what ships.
- **Re-review scope:** correctness and security, over the heap-accounting fix.
