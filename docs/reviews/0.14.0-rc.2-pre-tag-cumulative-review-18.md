## Blockers

### M1 (security, verified, treated as blocking): the membrane thins Array subclass instances and prototype-lying array Proxies — `src/vm/runtime.ts` ~750 / `readArrayData` ~985, ~1025

- **What happens:** in `membraneValue`, the `Array.isArray(v)` branch goes straight to `readArrayData`, which never reads `Object.getPrototypeOf(v)`. Every array copy then gets `Array.prototype` unconditionally.
- **Reproduced on HEAD with `transpile()` output:** an `effects: 'io'` atom returns `{ rule: new (class Rule extends Array { get denied() { return true } })() }`. The guest reads `x.rule.denied` and gets `undefined`, with no refusal and no error.
- **Also affected:**
  - The run-argument path is reported affected by the lens but was not independently re-confirmed.
  - A Proxy over an array whose `getPrototypeOf` trap lies goes through the same unchecked branch.
- **Why it matters:**
  - The object path and the Date path both refuse a non-exact prototype for exactly this reason: M-2, where a negated rule over a thinned getter turns deny into ALLOW.
  - CLAUDE.md: "A class instance is REFUSED, not thinned."
  - The behaviour predates the base, but "predates" is not a reason to defer.
- **Fix:**
  - In the array branch, refuse with kind `'shape'` unless the prototype is exactly `Array.prototype`, using the same "instance of <name>" wording the object path uses.
  - Add membrane-halt rows for an Array subclass with a prototype getter, and for a Proxy over an array that reports a non-Array prototype.
  - Cover both the capability return and the run argument, and assert the refusal rather than a thinned value.
  - Decide deliberately how cross-realm arrays (iframe, node:vm) should behave. They will now be refused, as cross-realm plain objects already are. Record that in the CHANGELOG as a consumer-facing change.
- **Fold in:** verified minor C1 below. It is the same walk and the same "the host decides the copy's shape" problem.
- **Re-review scope:**
  - Security over the whole array branch and `readArrayData`. Enumerate every host-observable trap: `getPrototypeOf`, `ownKeys`, `getOwnPropertyDescriptor`, `isArray`.
  - Then correctness and blast-radius over the remediation diff.

## Round 44 — plan (written before any code, per the cycle STOP)

**The underlying problem.** Each branch of the walk applied its OWN admission rule: the object
branch checked the prototype, the Date branch checked the prototype, and the array branch,
reached first through `Array.isArray`, checked nothing. That is the per-site shape again. **One
admission step runs for every object before any branch builds anything:**
- read the prototype once;
- the only admitted kinds are an array with exactly `Array.prototype`, a `Date` (by brand) with
  exactly the captured `Date.prototype` and no own keys, and a plain object with
  `Object.prototype` or `null`;
- everything else is refused as `'shape'` with one message naming the class (a subclass, a lying
  Proxy, a cross-realm array or object).
The branches then only build.

1. **M1** as above. Rows, as capability return AND run argument: an Array subclass with a
   prototype getter, a Proxy over an array reporting a non-Array prototype, a `Date` subclass
   (already refused), and a class instance (already refused). Each asserts the refusal, never a
   thinned value.
   - **Cross-realm arrays** (another iframe or `node:vm` context) are now refused, as cross-realm
     plain objects already are. The CHANGELOG says so; a host converts with JSON round-trip.
2. **C1:** in `readArrayData`'s `Object.keys` loop, an index key at or past the validated length
   is refused (`'shape'`): a genuine array cannot report one. Row: a Proxy with length 0 and key
   `'4294967294'` is refused, and no copy is longer than its validated length.
3. **C2:** comments, the guest-key-writes reasons and a describe title are corrected to the actual
   rule (arrays built null-prototype and patched; objects built on their prototype and defined).
4. **Lessons routed:** a card for the shared-practices write-back (optional globals,
   descriptor-only walks), since review 17's "already carded" was not true.
5. **Release-tree preconditions** (bump, CHANGELOG heading, push, `release:ready`, attestation)
   remain Tonio's go.

Re-review scope: security over the whole admission step and `readArrayData` (every
host-observable trap), then correctness + blast-radius over the diff.
