## Findings

### Nit

- **(unverified, but the code matches) The per-atom deadline is measured with the wall clock.** `src/vm/runtime.ts:5554` sets `const startedAt = Date.now()`. Line 5577 arms the timer with `Math.max(0, armedTimeout - (Date.now() - startedAt))`.
  - If the clock steps forward (an NTP correction, say) between the call and the `settledNow` check, the timer is armed at 0ms. An IO atom still inside its budget then fails with `Atom 'x' timed out`.
  - If the clock steps backward, the timer runs past `timeoutMs`.
  - Before round 47 the delay was the constant `armedTimeout`, so the clock could not affect it. Round 47 added this exposure when it fixed review 20 nit 4 ("deadline counts from the call").
  - Impact is low: the window is the microseconds between the call and the check, and a clock step has to land inside it. It is still a correctness regression in a timing path that matters for security.
  - **Fix:** use `performance.now()` (monotonic in Bun, Node and browsers) for both `startedAt` and the elapsed-time read, and keep the `Math.max(0, …)` clamp. It is a two-line change. Per the repo's bug-fix rule it needs a reproduction test first, e.g. stub `Date.now` to jump during a pending atom and assert the atom does not time out early.
