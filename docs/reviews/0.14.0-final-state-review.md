## Blocker

### B-1: Eval's `maxSourceBytes` does not measure the context keys spliced into the wrapper, which reopens the pre-fuel transpile DoS *(verified; security)*

`src/lang/eval.ts:155-173`. `checkSourceSize(code, …)` measures only `code`. The wrapper then adds `function __eval({ k1, k2, … })` to the source, and that key list has no bound. `transpile(wrappedCode)` runs before fuel or `timeoutMs` apply, and the whole call costs about 10-80 fuel.

The time grows super-linearly with the number of keys (N):

| N keys | Time (finding) | Time (verifier) |
|---|---|---|
| 1k | 34 ms | 19 ms |
| 20k | 2.0 s | 0.65 s |
| 40k | 7.4 s | 1.6 s |
| 80k | 22.3 s | 6.7 s |

The old wrapper handled 80k keys in 0-2 ms.

Who can reach it:
- `functions/src/index.tjs` passes `context: args` at three sites (lines 152, 260 and 386).
- For stored functions, `args = {...params, ...req.query, ...req.body}`.
- A function with `public: true` requires no authentication.
- The explicit `maxSourceBytes: 64*1024` on the run endpoint never sees the keys, even though that cap exists to close exactly this DoS. The gate fails open.

The hosted functions are pinned to `^0.13.11`, so they become exposed on their first lockfile refresh after 0.14.0. Library consumers who follow the Safe Eval chapter and pass request data as `context` are exposed as soon as 0.14.0 is published.

**Fix:**
1. Measure what actually reaches the transpiler: call `checkSourceSize(wrappedCode, …)`, or check `code.length + signature.length`.
2. Cap the number of declared keys (for example 1,000), with an error that names the limit.
3. Better still, declare only the keys the code references. This also fixes m-1.
4. Add a hostile-input test to `src/safe-eval-doc.test.ts`: a context with enough keys to exceed 64KB must return `{ error }` promptly, without transpiling.

**Re-review scope:** correctness + security over the `eval.ts` remediation diff and its new test. Also confirm that the functions endpoints' explicit `maxSourceBytes` now covers `args`.

## Majors (not blocking on their own, but they are open correctness issues, so fix them in the same remediation)

### M-1: Under TjsStrict, a converted TS parameter typed `{…} | null` throws a raw `TypeError` on null *(verified; correctness)*

`src/lang/emitters/js.ts:771` (also line 707).

fromTS turns `export function f(x: { a: string } | null)` into `f(x: { a: string } | null)`. The object-ness check lets `null` through, but `generateMemberCheckLines` then reads `x.a` with no null guard. Result: `f(null)` throws `TypeError: null is not an object`. It is thrown, not returned as a MonadicError, and the input is valid TS.

At base, converted code ran with `safety none` and returned 0. The same crash already existed in native `.tjs` at base; this diff (TjsStrict now turning validation on) is what makes converted code reach it. A `Type T = {a:''} | null` accepts `null`, so an inline shape and a named Type now disagree. Nested nullable members recurse without a guard as well.

**Fix:** wrap the member checks in `if (access != null) { … }` when `type.nullable` is set, recursively. Add rows to `tjsstrict-safety.test.ts` for the converted case and the native `.tjs` case.

### M-2: `optionalExample`'s `/\bundefined\b/` substring test makes nested optional members REQUIRED *(verified; correctness)*

`src/lang/emitters/from-ts.ts:402`, used at lines 714, 780 and 1279.

For `interface A { name: string; b?: { c?: string } }`, fromTS emits `b: { c: '' | undefined }` without `| undefined` on `b`. Under TjsStrict, `fa({ name: 'x' })` then returns `Expected A … got object`. `interface C { tags?: (string | undefined)[] }` fails the same way. The control `b?: { c: string }` converts correctly, which isolates the regex as the cause. Nested optional options objects are everyday TypeScript.

**Fix:** decide optionality from the top-level union members only (split on top-level `|`), or have `typeToExample` return a structured `optional` flag. Add the three shapes above to `from-ts.test.ts` and `tjsstrict-safety.test.ts`.

### M-3: Any kind marker, including a plain TS `number`, inlines the whole recursive-Type solver *(verified; efficiency)*

`src/lang/emitters/js.ts:1769/2114/2143`. `needsKind` is a single substring test for `__tjs_rt.__k(`, and when it matches, the whole solver is inlined: `__kSolve`, `__kLook`, `__kEval`, `__kExact`, `__kNode`, `__kFlip`, `__kPar`, `__kNorm`, `__kRec`, `__kKeys` and `__kWarn`.

Take `export interface Point { x: number; y: number }` plus one function. With `number` fields the output is 8,180 B (3,150 B gzipped); with `string` fields it is 1,884 B (879 B gzipped). That is 4.4x. The solver is dead code in this module, because `__kRec` is false for a non-recursive Type.

The cost is paid per module, since every emitted file carries its own inline runtime. For effect's 363 files, the finding extrapolates about 1.5 MB of duplicated solver code. The verifier did not measure that figure but confirmed the mechanism.

**Fix:** split the flag. Inline the basic marker helpers whenever a marker appears, and inline the solver only when the output contains a `ref` or nested-runtime-type marker. Add an emitted-size row that pins the fromTS interface case.

**Re-review scope (M-1 to M-3):** correctness + blast-radius over the remediation diff, including the oracle, example-kinds and predicates suites. The solver/non-solver boundary is a correctness boundary.

## Completeness gaps (must be closed before a GO)

1. **Diff basis is narrower than what ships.** This review covered `4c6bcb4..HEAD` (14 commits, 59 files). 0.14.0 as published is `v0.14.0-rc.0..HEAD`, 44 commits. The 30 commits in `rc.0..4c6bcb4` (fromTS class totality, ambient statements, class metadata, doc-site reorganisation, release tooling) have had only narrow delta reviews. **Run one whole-state review of rc.0..HEAD before tagging.**
2. **The release gate was not run on HEAD.** `.release-gate` stamps `551c290`, 18 commits old, and `dist/` was built before the HEAD commit. None of the following has run on this state: plain `bun test` (benchmarks, live LLM smoke, dependency audit), `bun run make` followed by the generated-artifacts `git diff --exit-code` (`demo/docs.json` and `docs/tjs-vs-typescript.md` both changed), `build:demo` / demo-bundle, bundle-size, or browser-bundle. The "standalone ~500 bytes" and size-budget claims were not re-measured now that the solver is inlined. Run `bun run release:ready` on the remediated HEAD.
3. **Version skew with an older installed runtime.** Tracked as m-6.
4. **Error-propagation semantics as a migration surface.** Removing the "any Error returns early" pre-check means functions now RUN on some error values they used to short-circuit on, and the `typeError` / `instanceTypeError` signatures in `tjs-lang/runtime` have changed. Not yet checked against downstream consumers (tosijs-ui live-example, `functions/*.tjs` once rebuilt on 0.14) or against the AJS/VM error-flow path.
5. **Eval surface not covered by B-1 / m-1:**
   - (a) Context keys can shadow builtins and atom names such as `JSON`, `Math` and `console`.
   - (b) Context VALUES are passed to `vm.run` as args. Do they go through the same membrane and ownership checks as capability returns, including host objects with methods or getters?
   - (c) The `SafeCapabilities.fetch` type change breaks the TypeScript signature for consumers, and `.d.ts` compatibility for `tjs-lang/eval` was not checked.
   - (d) `hasReturn = /\breturn\b/` is literal-blind (a `return` inside a string matches), and it now decides where the signature is placed. Add a row to `literal-blindness.test.ts`.
6. **Solver behaviours not covered by the oracle:**
   - `__kExact` swallows a `RangeError` thrown by a user predicate and treats it as `false`, with nothing recorded.
   - Re-entrancy within one file is unverified: the module-level `__kS`, `__kRu` and WeakMaps are shared if a predicate calls a TJS function that starts its own solve.
   - `__kBudget = 4e6` now rejects large legitimate recursive values, and this fail-closed behaviour is neither evaluated nor documented.
7. **Type-metadata consumers were not checked against the new `__k` markers and example kinds:**
   - The `metadata-cache.ts` IndexedDB cache may serve metadata in the pre-change shape after an upgrade. Is the cache versioned?
   - Editor autocomplete and introspection.
   - `json-schema.ts` / `toJSONSchema`, beyond the known recursive truncation.
   - The dts emitter for recursive Types.
   - Whether the shared `parser-params` accepts and rejects the new type-expression forms the same way on the AJS path as on the TJS path.
8. **New regexes: literal-blindness and ReDoS.** The new regexes in `dts.ts detectExports` (async, generator and anonymous default exports) run over unmasked source, and it is not visible that `literal-blindness.test.ts` covers them. `self-redos.test.ts` should cover the new patterns in `parser-transforms.ts` (`readTypeExpression`, `markExampleKinds`).
9. **Lenses that did not run:**
   - **docs:** the CHANGELOG, README size table, `type-identity.md` and the Safe Eval chapter were all rewritten, and m-5 already shows the numbers disagree.
   - **coverage:** a mutation-level check is needed on the new `typeError` branches and on the Eval key filter (RESERVED, FORBIDDEN and non-identifier keys).
   - **dx:** TjsStrict now turns safety on for all converted TS. That is a behaviour change for every existing TjsStrict user, and DOGFOOD_STRICT only covers this repo. M-1 and M-2 are two examples of the change surfacing.

No failing or skipped tests were reported by the coverage lens in this run. The five env-only failures seen in the scratch `git archive` copies (no `.git`) appeared at both base and HEAD. Confirm they do not appear on a real checkout during the `release:ready` run.
