## Findings

### Minor

1. **An `override`-only constructor parameter property loses its `this.a = a` without warning.** Lens: correctness. Verified (confirmed).
   - Location: `src/lang/emitters/from-ts.ts:~2433–2452`.
   - Input: `class B { a = 0 }` and `class C extends B { constructor(override a: number) { super() } }`.
   - What happens: tsc emits `this.a = a`. fromTS emits `constructor(a: number) { super(); }`, so `new C(5).a === 0`, with no throw and no warning.
   - Cause: the `paramProps` filter matches only public, private, protected and readonly. `checkModifiers` never runs on constructor parameters.
   - Why it matters for this release: the defect predates `81de3a6`, but CHANGELOG.md:226 now says the transform "classifies every member kind and modifier, and refuses anything it cannot classify". This input falsifies that claim, through the same silent-drop mechanism the commit set out to close.
2. **The decorator refusal gives the wrong reason** (unverified). Lens: correctness + blast-radius (merged).
   - Location: `src/lang/emitters/from-ts.ts:~2222–2224` and the CHANGELOG paragraph.
   - The message tells users their decorators have LEGACY `(target, key, descriptor)` semantics. That is only true under `experimentalDecorators`; the TypeScript 5 default is TC39 decorators.
   - Refusing is still the right call. fromTS reads no tsconfig, and the TJS parser cannot carry `@` (acorn: `Unexpected character '@'`). Only the stated reason is wrong, and every user who hits the refusal sees it.
3. **The CHANGELOG does not say that `fromTS` now THROWS where it used to return output** (unverified). Lens: blast-radius.
   - Location: CHANGELOG.md:209. The change is filed under "Fixed" as a conversion-quality change.
   - Who is affected: outside programmatic callers of `tjs-lang/lang/from-ts` and the browser from-ts bundle, such as codemods or batch scripts over NestJS, TypeORM or Angular trees. After upgrading, a whole run aborts on the first decorator or `accessor`, with a plain `Error` they cannot tell apart from a converter crash.
   - In-repo callers are unaffected: the CLI `convert` command, the TS playground and the compat lanes all catch the error.

### Nit

4. **Two new behaviours have no test** (unverified). Lens: correctness.
   - Erasing a bodyless (abstract) accessor: nothing in `src` mentions `abstract get` or `abstract set`. Deleting the new `continue` would bring back `get x() { }` (which returns undefined), and the suite would stay green.
   - The refusal branch in `checkModifiers` for an unlisted modifier is never exercised.
