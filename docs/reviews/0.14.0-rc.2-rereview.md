## Blocker

### B1. B4 is not closed: guest-keyed `obj[k] =` remains in pick, omit, varsExport, agentRun and convertExampleToSchema (verified, confirmed twice, by correctness and security)
- **Where:** `src/vm/runtime.ts`
  - `pick` at about line 3963: `res[k] = resolvedObj[k]`
  - `omit` at about line 3982: same assignment over `Object.keys`
  - `varsExport` at lines 3458 and 3462: `result[alias] = …`
  - `convertExampleToSchema` at line 1471: `properties[key] =`
  - `agentRun` at line 4408: `resolvedInput[k] =`, which sets the sub-agent's args prototype
  - `setGuestKey` is called at only four sites: 1331, 1608, 2635 and 2778.
- **Failure:** `JSON.parse` and `Object.fromEntries` both produce an own `__proto__` key. Passing that object through `omit` or `pick` makes the key the prototype of the result.
  - `omit({obj: JSON.parse('{"__proto__":{"hidden":1},"a":2}'), keys:['a']})` returns an object where `.hidden` reads 1 and `Object.keys` is `[]`.
  - Heap repro with an 8MB `maxHeapBytes`: six rounds of `Object.fromEntries([['__proto__',{s: 1.6MB}]])` passed through `omit` or `pick`, then `e = null`. The run holds about 19MB with no error. The control run fails with "Heap limit exceeded".
  - The `varsExport` alias form is reachable from any hand-built or JSON AST, which is the recommended `vm-ast` path.
- **Also wrong:** the CHANGELOG line "guest code cannot set an object's prototype" is false at HEAD.
- **Fix:**
  - Route every one of these sites through `setGuestKey`, including the legacy `return` projection's `res[key]`. Grep `\w+\[\w+\]\s*=` in runtime.ts for any others.
  - Add hostile-input rows (omit, pick, varsExport-alias, agentRun) to `rc2-review-blockers.test.ts` or `heap-scope.test.ts`. Each row should assert both that the key is refused and that the heap cap trips.
  - Add a structural guard: a parsed source scan that fails on a non-literal-key `obj[k] =` in runtime.ts outside `setGuestKey`. Two rounds have now missed sibling sites, so a sweep done by hand is not enough.

## Majors (verified; fix in the same remediation)

### M1. The B5 `inputsResolvedContext` spread drops lazily created heap accounting, so nested writes go uncounted (verified; regression in 30ea7c8)
- **Where:** `src/vm/runtime.ts:2752`, `src/vm/vm.ts:449`
- **Cause:** The root ctx does not pre-create `heapAccount` or `heapPerKey`; `trackHeapWrite` creates them with `??=` on whatever ctx it receives. A `resolveInputs: true` (default) control atom that runs `ctx.resolver('seq').exec(...)` as the run's first state write creates the accounting on the throwaway spread copy.
- **Repro, 8MB cap:** six 1.1MB strings bound inside the wrapper, then two at top level.
  - HEAD: the run succeeds.
  - 52aa804: the same run gives "Heap limit exceeded".
- **Why a CHANGELOG note is not enough:** the only safeguard is a CHANGELOG sentence, and CLAUDE.md #38 says documentation is not a control.
- **Same root, reported as a completeness gap (probed, not adversarially verified):** `createChildScope` spreads `inputsResolved: true` into every child, so `resolveValue` becomes the identity for the whole nested program. A nested `varSet` stores the raw `{$expr:'binary'}` node instead of 3, silently. rc.2 handled this correctly, so it is a regression for embedder control atoms.
- **Fix:**
  - Initialize `heapAccount: {bytes:0}` and `heapPerKey` (via `ledgerFor`) on the root ctx in vm.ts and on agentRun's hand-built contexts.
  - Have `createChildScope` and `seq.exec` clear `inputsResolved`, or throw when they run under it.
  - Add a test: a wrapper atom running nested steps first in the program, asserting the heap cap trips and nested expressions resolve.

### M2. runCode isolation covers only rebinding; guest source can mutate the caller's arrays in place (verified; latent since rc.1)
- **Where:** `src/vm/runtime.ts` around line 4666, plus `SCOPE_ROOTS` and `ownerOf`
- **Repro:** the caller has `let list = ['https://safe.example']`.
  - runCode `list.fill('https://evil')` leaves the caller with `['https://evil']`.
  - `list.push(...)` appends to the caller's array.
- **Why it matters:** this is the same threat model as B2 (model-written source redirecting fetch targets), reached when the targets sit in an array. The comments "isolates its variables" (lines 3329 and 4664) overstate the guarantee.
- **Fix:** decide the contract and pin it with a test. The options are:
  - (a) copy values read across a SCOPE_ROOT;
  - (b) refuse in-place mutators (`push`, `pop`, `shift`, `unshift`, `splice`, `fill`, `copyWithin`, `sort`, `reverse`) on values owned outside the current root;
  - (c) at minimum, document "runCode cannot rebind the caller's variables; values it can read it can mutate".
