## Blockers (must clear before `npm publish`)

### B1. The shipped CHANGELOG states a registry action that never happened — *verified ×4, re-verified live this session*
`CHANGELOG.md:18` asserts, unhedged and bolded: *"0.13.0 is **deprecated on npm** in favour of this release."*

Live registry check (`curl https://registry.npmjs.org/tjs-lang`) this session:
```
dist-tags: {"latest":"0.13.0","beta":"0.13.0-beta.1"}
0.13.1 published: false
deprecated versions: ['0.8.0']
```
0.13.0 carries no `deprecated` field. Neither does 0.12.0. `CHANGELOG.md` is in `package.json`'s `files`, and `demo/docs.json:845` mirrors it to the live playground — so the false claim ships to two consumer-facing surfaces the moment publish runs.

**Two aggravating facts:**
- The only queued deprecation is `npm deprecate 'tjs-lang@<0.13.0'` (`UPSTREAM.md:52`, `TODO.md:2859`). `<` is strict — it **excludes 0.13.0**. Running the queued step as written would still leave line 18 false.
- That queued step was already owed at 0.13.0's publish and was skipped. Base rate for "it'll get done at publish" here is 0/1.
- Published `0.12.0` declares `tosijs-schema: ^1.4.0`; upstream latest is 1.7.0, so a fresh install today fails with `Output validation failed for 'llmPredictBattery'`, and `^0.12.0` cannot float to a fix under 0.x semver. `npm deprecate` is the **only** channel that reaches those users.

**Fix (pick one, both cheap):** run `npm deprecate 'tjs-lang@0.13.0' …` **and** `npm deprecate 'tjs-lang@<0.13.0' …` (user action — npm auth), read the state back with `npm view tjs-lang@0.13.0 deprecated`, then publish. *Or* rewrite line 18 into the future tense and regenerate `demo/docs.json` (`bun run docs`). Do not ship an intention written in the indicative.

### B2. The symlink-walk fix reached one of three walks — false green in `check`, aborts and out-of-tree writes in `emit`/`convert` — *verified ×3*
One root cause, two user-visible halves. `src/cli/walk.ts` `findFiles` moved to `readdirSync(dir, {withFileTypes: true})` (a Dirent for a symlink is neither `isFile()` nor `isDirectory()`), but `emit.ts:242` and `convert.ts:172` still do `readdirSync(dir)` + `statSync(inputPath)`, which follows links. Only the two-line `shouldDescend` exclusion was shared.

**(a) Regression — `check`/`test` now silently skip symlinked source files.** A symlink to a real `.tjs` is neither descended nor collected. Reproduced: `tjs check proj` prints only `✓ proj/ok.tjs` and **exits 0**, while `tjs check proj/broken.tjs` on the same file reports `✗ … Function signature example is inconsistent`. `tjs test` is worse — a symlinked failing test file yields `0 pass / 0 fail / Ran 0 tests` with no diagnostic. 0.13.0's `statSync` walk followed the link and checked it. This is a type checker reporting green because it skipped the file — verbatim the failure mode CLAUDE.md's CI section names ("a guard that skips reports exactly the same green as a guard that passes").

**(b) Pre-existing — the two commands that WRITE still carry all three hazards.** Reproduced against HEAD: a dangling link makes `tjs emit -r` / `tjs convert -r` die with a raw `ENOENT … stat` and emit **zero** files (a valid sibling is lost); a symlinked directory makes `emit -r` write `out/link/secret.js` from a file **outside the tree the user named**, while the tally still says "1 emitted"; a cycle recurses 33 levels, writes 33 nested copies, then dies with `ELOOP`.

The CHANGELOG says the fix means "both hazards stop by construction" and `walk.ts`'s docstring reads as if all three walks now agree. They do not.

**Fix:** hoist the entry listing next to `shouldDescend` in `src/cli/walk.ts` (e.g. `readEntries(dir): Dirent[]`) and route `emitDirectory`/`convertDirectory` through it, so there is one answer to "what counts as a child" as there now is to "do we descend". For (a), branch `entry.isSymbolicLink()` into a guarded `statSync` in try/catch — ENOENT skip, `isFile()` collect, `isDirectory()` refuse to descend. Extend `src/cli/walk.test.ts` to drive `emit -r`/`convert -r` end-to-end, and add the missing "symlink to a real source file" row.

### B3. `tjs emit` silently strips the `#!` line — *verified by direct reproduction this session*
`preprocess` (`src/lang/parser.ts:123`) blanks the hashbang in place for offset stability, and nothing re-prepends it. Reproduced on HEAD:
```
$ bun src/cli/tjs.ts emit bin.tjs -o bin.js   # exit 0, no warning
$ head -c 32 bin.js | od -c
0000000   c   l   a   s   s       M   o   n   a   d   i   c   E   r   r ...
$ grep -c 'usr/bin' bin.js
0
```
`chmod +x bin.js && ./bin.js` → shell syntax error. Same through the library: `tjs('#!/usr/bin/env node\nconsole.log(1)', {dialect:'js'}).code` returns 19 spaces then the body.

This is a **new-capability trap, not a regression** — 0.13.0 hard-failed with `Unexpected character '!'`. That is what makes it blocker-shaped: the release notes frame the fix as unblocking exactly this ("`check` green-lit bin scripts that `emit`, `run`, `types` and `test` all died on"), so the reader's next move produces a silently unexecutable artifact instead of the error that used to stop them. `tsc` and `esbuild` both preserve shebangs. Failure surfaces at invocation time — in CI or post-install.

**Fix:** return the stripped hashbang from `preprocess` (it already knows `end`), carry it on the transpile result, re-prepend it in `transpileToJS`'s final assembly **ahead of the inline-runtime preamble**. Pin it: a `subset-invariant.test.ts` row for `dialect:'js'` and native `.tjs`, plus a `check.test.ts` loop over `emit`/`run`/`types`/`test` asserting the emitted file's first line is the original `#!` and that it executes.
