## Blockers

Each item below is a confirmed major, promoted because it is an unresolved correctness or security problem.

### B1. `varGet` and `varsExport` return the variable NAME under AST v2 (correctness, confirmed)
- **Where:** `src/vm/runtime.ts:3294` (varGet) and `:3346` (varsExport).
- **What happens:** both look the variable up with `resolveValue(key, ctx)`. Under v2, `resolveValue` returns any bare string as a literal (line ~1212).
- **Repro:** `const x = 42; varGet({ key: 'x' })` returns `'x'`, and `varsExport({ keys: ['x'] })` returns `{x:'x'}`. There is no error. Both atoms are documented in DOCS-AJS.md.
- **Fix:** read the binding by name (scope lookup plus the forbidden-key check), independent of the AST version. Add v2 rows to `ast-v2.test.ts` for both atoms, including the array and alias forms of varsExport. Sweep the core atoms for any other name-typed input still passed to `resolveValue`.
- **Re-review:** correctness and blast-radius over the remediation diff.

### B2. runCode code can now overwrite the caller's variables (correctness and security, confirmed, regression from rc.1)
- **Where:** `src/vm/runtime.ts:4554` (runCode → `createChildScope`) and `:3243` (`ownerOf`).
- **What happens:** the child's state is linked to the caller's through the prototype chain, and `varAssign` writes to the scope `ownerOf` finds, which can be the caller's.
- **Repro:** the caller has `let target = 'https://safe.example'`, and the runCode source does `target = "https://evil.example"`. The caller ends with `evil.example`. rc.1 kept `safe.example`.
- **Why it matters:** the comment there says the scope "isolates its variables", and the docs say the same. Code passed to runCode is usually model-written. agentRun and callLocal are still isolated.
- **Fix:** add a scope-root marker that `ownerOf` (and ideally ident lookup) stops at, or give runCode a fresh `state: {}` plus explicit args. Add hostile-input tests in `scoping.test.ts` showing that runCode cannot assign to the caller's locals, and preferably cannot read them either. Check the other `ownerOf` callers (map, while).
- **Re-review:** correctness and security over the remediation diff.

### B3. `memoize` cache is lost on every iteration of a v2 `while` loop (correctness, confirmed)
- **Where:** `src/vm/runtime.ts:3039` (the while loop's per-iteration `createChildScope`) and `:4645` (`ctx.memo` created lazily).
- **Repro:** a 3-iteration while loop with a fixed memoize key runs the body 3 times under v2 and once under v1.
- **Why it matters:** an LLM or fetch call inside a loop is re-run and re-billed (fuel and quota) on every pass.
- **Fix:** set `memo: new Map()` on the root context in `vm.run`, and decide on purpose whether agentRun and runCode children share it. Add a test where memoize sits inside both while and for-of and the body runs exactly once.
- **Re-review:** correctness over the remediation diff.

### B4. A guest `__proto__` key in an object literal gets past `maxHeapBytes` (security, confirmed)
- **Where:** `src/vm/runtime.ts:2587`, `evaluateExpr` `case 'object'`.
- **What happens:** `result[prop.key] = …` with the key `__proto__` sets the object's prototype instead of adding a property. The heap walk counts only own properties, so whatever hangs off the prototype is never counted.
- **Repro:** with an 8MB cap, `{ $expr: 1, ['__proto__']: big }` five times holds about 15MB, and the guest can still read it through the prototype. The control, `{ inner: big }`, fails with the expected heap-limit error.
- **Why now:** e4dbb41 widened the route into this code path (any literal with a `$expr`/`$kind` key). The spread form reportedly also got past the limit at rc.1, but the verifier could not reproduce that.
- **Fix:** refuse `FORBIDDEN_KEYS_SET` keys when building guest objects: in `evaluateExpr` 'object', in `resolveValue`'s plain-object path, in `resolveAtomInputs` (`out[key]=`) and in spread desugaring. Better still, also reject them in the AJS emitter at transpile time. At minimum, use `Object.create(null)` or `defineProperty`. Add hostile-input rows to `heap-scope.test.ts`, and sweep `runtime.ts` for any other `obj[guestKey] =`.
- **Re-review:** security and correctness over the remediation diff.

### B5. `resolveInputs: true` default: atoms that already resolve their own inputs now evaluate guest DATA as code (blast-radius and security, confirmed)
- **Where:** `src/vm/runtime.ts:2730` (the default) and `:2819` (the wrapper resolves inputs).
- **What happens:** an embedder atom written the old, previously necessary way calls `resolveValue(v, ctx)` itself, so it now resolves an already-resolved value a second time.
- **Repro:** `let secret='TOPSECRET'; let data = { $expr:'ident', name:'secret' }; echo({ v: data })` returns `'TOPSECRET'`. The same happens when the data comes from `JSON.parse` of an LLM or httpFetch payload. Under v1 (builder) ASTs, a resolved string that matches a variable name is read again as that variable, which is the literal-redirect class this release claims to close.
- **Who is affected:** our own batteries and core atoms opt out, but embedders do not. snowfox-app has four custom atoms, and `src/use-cases/comparison.test.ts` and `ajs-grokkability.test.ts` use this pattern.
- **Why a doc line is not enough:** the CHANGELOG ("or it resolves twice") understates the consequence, and "documentation isn't a control" (#38).
- **Fix:** make the second resolution harmless. Run the atom with a context marked as having resolved inputs, and have `resolveValue` return its argument unchanged under that mark. Optionally also record a once-per-op 'vm' notice in the flight recorder. Rewrite the CHANGELOG entry to state the data-as-code consequence. Add a test with a self-resolving custom atom and `{$expr}`-shaped data.
- **Re-review:** correctness, security and blast-radius over the remediation diff.
