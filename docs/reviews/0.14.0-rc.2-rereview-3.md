## Blockers

### B1 (verified, correctness/security): mutation bytes are refunded while the referent is still live, so the heap cap is evaded
- **Where:** `src/vm/runtime.ts:2329` (`accountMutation`), together with `releaseScope` (around line 1180)
- **Repro:** run this through `transpile()` and `AgentVM.run` with `maxHeapBytes: 1_000_000`:
  `function f(){ let rows=[]; let k=0; while(k<50){ let r=[]; rows.push(r); let i=0; while(i<400){ r.push('x'.repeat(1000)+i); i=i+1 } k=k+1 } return {n: rows.length} }`
  It returns `{n:50}` while holding about 40MB under a 1MB cap.
- **Control:** making the same pushes straight onto `rows` fails correctly with "Heap limit exceeded … op: push".
- **Cause:** `r.push` charges `r`'s ledger entry (`entry.size += bytes`). The v2 while body is a per-iteration child scope, so `releaseScope` subtracts that entry at the end of each iteration. `rows.push(r)` charged only the empty array.
- **Second variant:** a helper `fill(a)` that pushes into its parameter has the same flaw, because the parameter's ledger entry is released when the call returns. This variant was reported but not run separately.
- **Why this is a blocker:** it is the same class as rc.2-rereview-2 B2 ("20MB under a 1MB cap"). `heap-mutation.test.ts` and `rc2-rereview-2.test.ts` only exercise receivers whose root binding lives for the whole program, so they cannot see this.
- **Direction:** decide the accounting unit before patching. The bytes belong to the referent, not to the name. One option:
  - Keep mutation-accrued bytes separate from the bind-time size in `HeapEntry`.
  - Do not refund them in `releaseScope`.
  - Reconcile them by re-measuring reachable values when the referent is rebound, or when the run total nears the cap.

  This fixes M1 at the same time. Add both programs as `transpile()`-level rows.
- **Re-review scope:** correctness and security over the heap-accounting diff (accountMutation, releaseScope, trackHeapWrite fast paths).

## Majors (must be resolved in the same remediation; both are correctness)

### M1 (verified, correctness): mutations through an unledgered root (a for-of alias, args) are charged permanently, so legitimate programs are falsely rejected
- **Where:** `src/vm/runtime.ts:2321`
- **Repro:** run with `maxHeapBytes: 1_000_000`:
  `function f(){ let k=0; let total=0; while(k<1000){ let rows=[[],[]]; for (const row of rows){ row.push('x'.repeat(1000)) } total=total+rows.length; k=k+1 } return {total} }`
  It fails with "Heap limit exceeded: guest state holds ~1MB", although the live heap is about 4KB.
- **Control:** a binding-rooted receiver in the same loop completes.
- **Cause:** `row` is bound with `alias:true`, which skips trackHeapWrite, so it has no ledger entry. `account.bytes += bytes` runs anyway and is never released.
- **Consequences:**
  - Under the default 64MB cap, about 64k pushes of 1KB through aliases trips the cap.
  - The error message misreports what guest state holds.
  - The code comment's claim that this is "an over-count, never an escape" contradicts the releaseScope doc's own rule that a cap enforcing what nobody asked for is a broken cap.
- **Fix:** fix this together with B1 through referent reconciliation. At minimum, re-measure the live bindings before raising the error. Add this loop as a must-pass row.

### M2 (verified, correctness / subset invariant): the const rule refuses legal JS where blocks share the enclosing scope, and adds a new catch refusal
- **Where:** `src/vm/runtime.ts:2551` (setStateVar const check). The catch binds through `setStateVar(ctx, 'errorOp', …)` at about line 3430.
- **Repros** (all through `transpile()`):
  - (a) `const e = 1; try { Error('boom') } catch (e) { got = 2 }` fails with "Cannot reassign const variable 'e'". **This is new in 0f09c1a.** Before the commit, the const was silently overwritten.
  - (a2) A user `const errorOp` breaks every subsequent catch.
  - (b) Sibling blocks `if (true) { const t = 1 } if (true) { const t = 2 }` are refused (constSet).
  - (c) `const x = 1; if (true) { let x = 2 }` is refused (varSet).
- **Why it matters:** this violates AJS ⊆ TJS ⊆ JS (PRINCIPLES.md). The docstring claims the rule is right "by construction", but that holds only for loop bodies. No test pins the catch behaviour in either direction.
- **History:** (b) and (c) likely predate the commit. Per project policy, "predates" is not a reason to defer.
- **Fix:** the rule is correct; give v2 if/else branches, try blocks and catch blocks their own `createChildScope`/`releaseScope`, as v2 `whileLoop` does. Bind `catchParam` and `errorOp` in the catch scope, and rename or hide `errorOp` from guest namespace collisions. Add `transpile()`-level rows for (a), (a2), (b) and (c).
- **Interaction:** new child scopes go through `releaseScope`, so this fix widens B1's refund surface. Land it only after the accounting unit is settled.
