## BLOCKER

### B-1 — Published deprecation metadata routes users ONTO vulnerable versions; no GHSA; the premise justifying inaction is false and ships in the tarball
`CHANGELOG.md:103` · *verified* · **distribution-only fix, no code change**

Live registry state, re-confirmed during triage:

- Only **0.13.7** is deprecated. **0.13.1, 0.13.5, 0.13.6 and 0.13.8 are not** — yet `CHANGELOG.md:103` states `tjs-lang <= 0.13.8` all carry at least one transpile-time execution path. 0.13.1's vulnerability was confirmed by inspection, not inference: `git grep "new Function" v0.13.1` → `src/lang/emitters/js.ts:1009`.
- **Five** machine-readable pointers aim users at vulnerable versions: 0.13.7 → "Upgrade to 0.13.8"; 0.10.0/0.11.0/0.12.0/0.13.0 → "Upgrade to 0.13.1"; 0.13.4 → "Fixed in 0.13.5".
- **No advisory exists** in any of three databases (GitHub repo advisories, the npm ecosystem feed, OSV.dev) — all returned empty. So `npm audit` and Dependabot report **zero** vulnerabilities for any pinned vulnerable version.
- `npm view tjs-lang dist-tags` → `latest: 0.13.9`. The fix is published and simply not being routed to.

The justification at `CHANGELOG.md:104` — *"this project has no known consumers, so the automated-notification machinery would be ceremony rather than protection"* — is contradicted by the repo's own files in five places (`reviews/0.13.8-post-remediation-review.md:29`, `TODO.md:3579`, `CLAUDE.md:553`, `CLAUDE.md:599`, `CHANGELOG.md:268`) and by **6,658 downloads in the last month**. `CHANGELOG.md` is in `package.json:files`, so the false premise ships. The prior review filed this as BLOCKER B-2; its checkbox at `reviews/0.13.8-post-remediation-review.md:79` is still unticked.

**Remediation (all distribution-side):**
1. `npm deprecate 'tjs-lang@<=0.13.8' "SECURITY: transpiling untrusted source can execute it at transpile time — upgrade to 0.13.10"`
2. Amend the 0.13.7 string so it no longer points at 0.13.8, and the 0.10–0.13.0 / 0.13.4 strings so they no longer point at 0.13.1 / 0.13.5.
3. File a GHSA (affected from 0.10.0, fixed in 0.13.9/0.13.10) — the only channel reaching `npm audit`/Dependabot.
4. Correct or delete `CHANGELOG.md:103-105` before it ships again; read state back with `npm view tjs-lang@<v> deprecated`.

## MAJOR (7) — all verified

### M-1 — `parse()` / `preprocess()` silently ignore the removed `vmTarget`, re-enabling transpile-time `new Function()` on a public export
`src/lang/parser.ts:674` · *verified (adjusted blocker → major)*

Before this diff `parse(src, { vmTarget: true })` was **safe** — the 0.13.7 gate suppressed `extractAndRunTests`. Now the option is destructured away and `extractAndRunTests` runs unconditionally (`parser.ts:541`). Reproduced: `parse("test 'x' { globalThis.__PWNED__ = true }\nfunction main(n: 0) { return n }", { vmTarget: true })` sets the sentinel. No throw, no warning, no flight-recorder entry. TypeScript catches only the inline-object-literal case; a JS consumer, a spread, or `as any` gets nothing.

The verifier found the fail-open is **broader** than reported: `vmTarget` also suppressed `==`→`Eq`, so a caller silently gets that transform back too. Downgraded from blocker because the documented AJS surface is closed (`Eval` rejects the carrier — confirmed) and the vulnerable-artifact window was ~7 hours, but this is precisely the "a gate fails OPEN" defect the release is named for. **Fix before tag** — throw when `'vmTarget' in options`, pointing at `parseAgentSource()`.

### M-2 — VM builtin allowlist and atom registry are looked up through the prototype chain; one path invokes a host function with guest arguments
`src/vm/runtime.ts:2382` · *verified*

`builtins` and `AgentVM.atoms` are plain object literals; both lookups use `in` / bracket access on an attacker-controlled key. Reproduced live via `Eval` (fuel 400, no capabilities): `return { v: constructor('abc') }` → `{"v":"abc"}` — the host `Object`, reached as `builtins.constructor`, **called with guest arguments** past the allowlist. `return { v: toString() }` → `"[object Undefined]"`. In statement position the `Unknown Atom` gate passes on an inherited value and dies on an internal `atom.exec is not a function` TypeError, which `functions/src/index.tjs:383` returns verbatim to the HTTP caller.

Verifier corrections, neither weakening it: **11** names resolve (not 8), and the leak also occurs one gate earlier at the `ident` path (`runtime.ts:2240-2250`, `ctx.state`/`ctx.args` are plain objects too). No escalation to `Function` (blocked by `assertSafeProperty`/`SAFE_METHOD_NAMES`), no prototype pollution — so not a blocker. Pre-existing (`81ef0dc`), untouched by this diff. Fix: `Object.create(null)` for both maps, or `hasOwnProperty.call` at the three lookup sites.

### M-3 — `Eval`'s fuel and timeout apply only *after* transpilation, which is quadratic and byte-uncapped at every layer
`src/lang/eval.ts:85` · *verified*

`src/lang/eval.ts:87` transpiles before `vm.run`, so `fuel`/`timeoutMs` bound nothing during compile. Verifier measurements (worse than originally reported): 109 KB → 2.0s, 447 KB → 12.6s, 905 KB → 35.8s, 1.8 MB → **144.6s**, with `fuelUsed` 0.2 at every size. Both public endpoints (`functions/src/index.tjs:143, 244`) validate only `typeof code === 'string'` and cap `fuel`, not bytes; no `timeoutSeconds`/`maxInstances`/concurrency config exists anywhere, so Firebase v2 defaults (60s) apply. One request from any free signed-in account pins an instance at zero metered fuel. On a path this release rewrites.

Two verifier corrections: `duration`/`totalDuration` **are** logged (so the ledger is not wholly blind — the metering story is), and the `page` endpoint re-transpiles on every request with no compile cache, so a large stored function pays the quadratic cost per hit with no attacker required.

### M-4 — The two `transpile()` copies have drifted; the canonical AJS entry signature gets **opposite** input contracts from the two entry points
`src/lang/index.ts:226` · *verified*

`core.ts:48-61` forwards `requiredValueOffsets`; `index.ts:226-238` omits it. In `emitters/ast.ts:158-164` the offsets branch only inspects top-level `AssignmentPattern` params, so a destructured `ObjectPattern` — which `DOCS-AJS.md:181` documents as *the* AJS entry shape — matches nothing, `requiredHere` is empty, and the name-based fallback is skipped. Reproduced against built bundles for `function agent({ apiKey: 'sk-example' })`:

- `dist/index.js` → `required: ['apiKey']`; `vm.run(ast, {})` → `Input validation failed` ✓
- `dist/tjs-lang.js` → **no `required`**; `vm.run(ast, {})` → `{"apiKey":"sk-example"}` — the example value (frequently credential-shaped) silently substituted for a missing required input ✗

Blast radius is **wider** than reported and crosses the entry boundary: `src/vm/vm.ts:15` imports `transpile` from `../lang/core`, so `vm.run(sourceString)` in the *main* bundle is also affected — one consumer gets the correct contract from `transpile()` and the broken one from `AgentVM`. The sibling emitter `emitters/js.ts:1229` handles destructured members correctly; `ast.ts` is the gap. Pre-existing, but both copies were touched here and the drift is now one line wide. The `export *` ambiguity aggravator was **refuted** (both paths resolve to the same module).

### M-5 — Both structural guards the release's security claim rests on are evadable by ordinary code
`src/lang/eval-no-transpile-execution.test.ts:218` · *verified* — merges three lens reports

`CHANGELOG.md:36` says a new transform "fails at the import"; `CLAUDE.md:195` says "nothing there can reach AJS". Both are false as written.

1. **Import pin matches only brace-form named imports.** `/^import\s*\{([^}]+)\}\s*from\s*'([^']+)'/gm` — `import * as T from './parser-transforms'` and `import dflt from './x'` both yield **0 matches** (run directly). Reproduced end-to-end: appending a namespace import of `parser-transforms` plus a use of it leaves the pinned set byte-identical and the guard green. Damning corroboration: `parser-agent.ts:37` **is already** `import * as acorn from 'acorn'` — invisible to the pin, while the expected list's first comment ("acorn — the parse itself") has slid onto `'./types:SyntaxError'`. The one import the author narrated is the one the guard cannot see. The `if (/^import\s+type/.test(m[0])) continue` at line 222 is dead — the outer regex can never match it.
2. **The dynamic-execution scan's `files` list is hand-maintained and incomplete.** A transitive walk from `core.ts` finds 35 reachable files, **26 outside the scan list**, including `emitters/ast.ts` (the AJS emitter, called on every piece of untrusted agent source), `inference.ts`, `expression-context.ts`, `tests.ts`, `given-transform.ts`, `wasm.ts`. A `new Function` in any of them runs upstream of fuel/timeout/capabilities/membrane — the same shape as the 0.13.7 RCE and the eight 0.13.8 emitter sites. Latent today (the only hits in those 26 are inside comments); the file currently passes 17/17.
3. **Depth-1 only, while both real AJS transforms are shared.** `transformParenExpressions` and `extractParamMarkers` live in `parser-params.ts`, called by both parsers — the "shared helper is a gate again" the header argues against. *Note: the dictionary-defaults evidence offered for this was **refuted** — AJS gets atomic JS defaults, correctly, and nothing regressed.*

Fix: parse `parser-agent.ts` with acorn (already a dependency) and pin resolved specifiers; replace the hand-written `files` list with the computed transitive closure.

### M-6 — `parseAgentSource` is not exported from `tjs-lang/lang`, so the CHANGELOG's migration instruction names an export that does not exist
`src/lang/transpiler.ts:14` · *verified* — merges correctness + efficiency

`CHANGELOG.md:43` tells `vmTarget` callers to *"call `parseAgentSource()` (exported from `tjs-lang/lang`)"*. It is not there, in **all three** export conditions: the bun/source path (`transpiler.ts` re-exports a *named* list from `./core`, not `export *`), the Node default (`dist/tjs-lang.js` exports `parse` and `preprocess`, zero occurrences of `parseAgentSource`), and types (`dist/src/lang/transpiler.d.ts` — so a TS consumer gets a compile error, not merely `undefined`). Confirmed in triage: `transpiler.ts:17` exports `parse` but no agent-parser name.

Two aggravators. The comment at `src/lang/index.ts:42` — "the pair is the visible form of the split" — is **false at the package boundary**: the public entry exports TJS's parser and hides AJS's. And the repo already has a guard for exactly this drift class, `src/package-exports.test.ts:176` ("the tjs-lang/lang subpath exports every documented name"), written after `functionMetaToJSONSchema` drifted identically, whose comment says *"If you document a new `tjs-lang/lang` import, add it here."* This release documented one and updated neither — **the guard passed vacuously.** The working fallback (`tjs-lang`) costs ~91 KB raw / ~29 KB gzipped more, landing on exactly the callers this release breaks.

Fix: `export { parseAgentSource, preprocessAgentSource } from './core'` in `transpiler.ts` next to `parse`, plus the entry in the existing guard list.

### M-7 — The project's own public endpoints run 0.13.8, and nothing gates it
`functions/package.json:21` · *verified* — merges security + blast-radius

Re-confirmed live in triage: `curl https://health-ldh7npl2bq-uc.a.run.app` → `{"status":"ok",…,"tjsLang":"0.13.8"}`. `functions/package.json:21` declares `^0.13.8` and `functions/package-lock.json` pins `0.13.8` with an integrity hash, so `npm ci` (what a Firebase deploy runs) reproduces it regardless of what ships. `functions/` is untouched by this diff, so 0.13.10 will not reach it either.

**Not a live exposure** — the deployed 0.13.8 build was probed directly with the test-block and annotation payloads and rejects all of them. The defect is that the public code-execution endpoints are two security-motivated releases behind, including 0.13.10 itself, whose CHANGELOG opens *"The structural fix behind 0.13.7's `test`-block RCE"* and closes seven leaks **on the exact path those endpoints run**. The one gate that looks at `functions/` (`src/dependency-audit.test.ts:59`) only sees `bun audit` advisories, and the 0.13.9 CHANGELOG states no advisory was filed — structurally unable to see this. `cac3c62` records the identical failure once already ("the deployed VM was pre-0.12 — no membrane, on a public endpoint").

*Framing nit: `^0.13.8` is a caret range that permits newer; the real pin is the lockfile, which is correct behaviour. The defect is the absent process gate.*

## MINOR (5)

### m-1 — TJS safety markers leak onto the AJS path through the shared `parser-params.ts`; "KNOWN_LEAKS is empty" overstates the result
`src/lang/parser-agent.ts:65` · *verified*

`preprocessAgentSource` hands `transformParenExpressions` throwaway `unsafeFunctions`/`safeFunctions` sets; the shared function strips the markers at `parser-params.ts:554-562` and the result is dropped. `function f(!a: 1)`, `f(? a: 1)` and the return forms `:!`/`:?` are all **accepted and silently discarded**; the arrow form `(! x) => x` even *injects* a `/* unsafe */` comment into AJS source. Per `CLAUDE-TJS-SYNTAX.md:150` a leading `!` disables all validation, so an author writing `function main(!apiKey: '')` gets the opposite of what the marker documents, with no diagnostic. This directly falsifies `parser-agent.ts:60-63`, which lists "`unsafe` markers" among the things "absent by construction". No execution, no capability, no fuel bypass — hence minor. The ratchet's `CONSTRUCTS` list has no safety-marker row, so the empty `KNOWN_LEAKS` cannot see it.

### m-2 — `parseLiteralValue` never checks it consumed the whole input
`src/lang/literal-value.ts:159` · **confirmed in triage** (was unverified)

`parseLiteralValue("0; globalThis.__TRAILING__ = 1")` → `{ ok: true, value: 0 }`, sentinel `undefined`. Nothing executes, but this is the 0.13.9 hardening whose stated rule is that the listed node types are *the entire accepted grammar*. A grammar check that ignores its tail accepts inputs the doc says it refuses, and the emitters then embed a value the annotation did not specify. Fix: `if (node.end !== trimmed.length) return { ok: false, reason: 'trailing content after the literal' }`.

### m-3 — `literal-value.ts` lets an example value choose the reconstructed object's prototype
`src/lang/literal-value.ts:127` · **confirmed in triage** (was unverified)

`parseLiteralValue('{ __proto__: { polluted: 1 } }')` → `ok: true`, `Object.keys(value)` is `[]`, `value.polluted === 1`, `getPrototypeOf(value)` is `{ polluted: 1 }`. `Object.prototype` verified untouched — not global pollution. The cost is an example that means one thing to `Object.keys` and another to `for…in`/`in`. This is the one new file rebuilding objects from untrusted text and the one place that does not consult `src/forbidden-keys.ts`, the repo's canonical list for exactly this key.

### m-4 — README (shipped to npm) credits the 0.13.10 bundle win to 0.13.9
`README.md:225` · **confirmed in triage** (was unverified, reported by three lenses)

`README.md:225` reads "**Measured at v0.13.9**" and `:236` "The VM and eval bundles got **23%** and **40%** smaller in 0.13.9". The parser split ships in 0.13.10 (`package.json` 0.13.10; CHANGELOG dates it 0.13.10); v0.13.9 shipped the *old* sizes. A reader pinning 0.13.9 for the 218 KB VM gets the 283 KB one. `src/bundle-size.test.ts` re-measures the numbers but only asserts *some* `/Measured at v\d+\.\d+\.\d+/` exists, so the version stamp is the one part of the table that can still rot silently — in a section whose stated purpose is that a checkable claim earns trust in the unverifiable security claims beside it.

### m-5 — `CLAUDE.md:655` still documents the removed `vmTarget` as a dialect-inference input
`CLAUDE.md:655` · **confirmed in triage** (was unverified)

Reads *"`dialect` is authoritative; otherwise inferred from the `fromTS` annotation / `vmTarget`."* `CLAUDE.md` is in `package.json:files` and `llms.txt` routes agents to it first — a shipped instruction pointing at a removed flag, landing readers on M-1's silently-ignored path. The twin sentence in `parser-types.ts` **was** updated by this diff; the doc copy was missed.

## Correction — 2026-09-03, after filing

**B-1's severity rested on a number that does not mean what the review took it to mean.**

The report cites *"refuted outright by 6,658 downloads in the last month"* as proof that the
CHANGELOG's "no known consumers" was false, and rates B-1 a blocker partly on that basis. The
maintainer asked whether those downloads were just our own CI. They are.

Evidence, gathered after filing:

- **Per-version** (`api.npmjs.org/versions/tjs-lang/last-week`): `latest` (0.13.9) has **zero**
  downloads. Traffic instead spreads across nine older versions — 0.13.5, 0.13.4, 0.13.6,
  0.13.3, 0.12.0, 0.9.0, 0.8.1, 0.3.0, 0.2.8 — and **each maps to a lockfile in one of the
  maintainer's own repos** (`tosijs`, `tosijs-ui`, `tosijs-3d`, `tosijs-product`,
  `loewald-dot-com`, `falling-forward`, `lukko`, `ajs-clawbot`, `ngx-tosijs`). `tosijs-ui`'s
  live-example component depends on `tjs-lang`, so every one of those projects' CI runs pulls
  it.
- **Per-day** (`downloads/range/last-month`): a **zero-download day** (2026-08-14), which a
  distributed consumer population does not produce; and the largest spike (2026-08-25, 1,111)
  falls exactly on the day `functions/` gained its `^0.13.3` pin.
- A public package also carries a nonzero floor from registry mirrors and scanners.

**What this changes.** The affected population is the maintainer's own projects plus
**snowfox-app** — a named production consumer, documented in five places in the repo, and
better evidence than any download total. So:

- Fixing the five deprecation strings that point at vulnerable versions **stands** — wrong at
  any audience size, minutes to fix.
- `npm deprecate` over the range **stands** — cheap and correct.
- **Updating our own nine repos is the real remediation**, and was not in the report at all.
- Messaging snowfox-app directly beats an advisory.
- **The GHSA is now optional**, and per `releasing.md`'s existing "Responsibility scales with
  the MEASURED user base — don't cosplay Firebase", arguably should not be filed unless
  tjs-lang is being presented as a package outsiders should depend on.

**The methodological lesson, which is the durable part.** The review refuted an unmeasured
assertion with an unvalidated number — the same error inverted. A download count measures
installs, not adopters, and for a package pulled in by a shared internal component it measures
mostly your own CI. Per-version and per-day breakdowns settle it in about two minutes and
should precede any citation of a download total. Written back to
`tosijs-coding-practices/practices/releasing.md`.

Recorded as an appendix rather than an edit to the body: the report should show what was found,
including where it was wrong.

## Correction 2 — 2026-09-04: B-1 was mis-sequenced, and the affected range is now measured

**The blocker was a deadlock.** B-1's remediation directs users to upgrade to 0.13.10, while
the verdict withholds the tag until B-1 clears. You cannot point a deprecation at a version
that does not exist. B-1 is a **post-publish distribution action** — publish 0.13.10, *then*
deprecate in favour of it. The 0.13.8 review labelled this same item a "post-publish
distribution action" and then filed it as a pre-tag blocker anyway; this review repeated it.
**Nothing in B-1 needs to precede the tag**, so it should not have carried the BLOCK.

**The affected range, measured rather than assumed.** The report asserted "affected from
0.10.0". Probing published tarballs from Node with the test-block payload:

| Version | Result |
| --- | --- |
| 0.2.0 – 0.7.3 | **both entry points fail to import** — the broken subpath exports fixed by `f2ea1bc`. Not exploitable from Node because the package does not load. *Bun resolves `src/`, so Bun consumers of these may still be exposed.* |
| **0.7.4** (2026-04-14) | **first PWNED**, via `tjs-lang/eval` |
| 0.13.6 | PWNED |
| 0.13.7 | **still PWNED** — the release whose fix shipped in `src/` but not `dist/`; Node consumers get `dist` |
| 0.13.8 | safe for the test-block path (still carries the separate annotation escape, fixed in 0.13.9) |

**The mechanism is the interesting part, and it is not what "affected from 0.10.0" suggests.**
The vulnerable code path existed from **v0.2.0** — `47dcde7` (2026-01-19) put `extractAndRunTests`
into the shared `parse()`, which the AJS entry already called. It sat unreachable for three
months because the package's subpath exports were broken. The commit that armed it was
`f2ea1bc — "v0.7.4: fix broken subpath exports, switch build to esbuild"`: a **packaging fix**
turned a latent bug into a live RCE, touching no parser code.

Worth carrying forward: "when was this introduced?" and "when did it become reachable?" are
different questions, and for a vulnerability only the second one bounds the affected range. A
`git log -S` on the vulnerable function finds the first; only installing the published
artifacts finds the second.
