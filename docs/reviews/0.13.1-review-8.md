## 🔴 Blocker — must be fixed and shipped as 0.13.2

### B1 · The hashbang fix was applied at the wrong seam — it is baked into `result.code`, breaking a published bin, the documented library idiom, and the playground
`src/lang/emitters/js.ts:1960` · **verified by six independent lenses, reproduced this session**

`transpileToJS` now returns `code: hashbang ? \`${hashbang}\n${code}\` : code`. But `code` is a **fragment**, and `#!` is legal only at absolute offset 0 of a Script/Module. Reproduced against HEAD *and* confirmed present in the published `tjs-lang@0.13.1` tarball:

- `bun src/cli/tjsx.ts g.tjs --name=bob` → `Runtime error: Invalid character: '#'` — **`tjsx` is a published `bin` entry** (`src/cli/tjsx.ts:130` wraps `${result.code}` in `new Function`).
- `new Function(result.code + '\nreturn fnName')()` → same error. That is verbatim the idiom **CLAUDE.md** prescribes under "Running Emitted TJS Code", and CLAUDE.md is in `package.json` `files`.
- `demo/src/playground-shared.ts:117` and `demo/src/module-store.ts:248` have the same shape → the playground preview and its inline-test runner die on any pasted bin script.

Not a cross-release regression (0.13.0 rejected `#!` at parse with `Unexpected character '!'`), so nothing previously working broke — but a headline feature is half-delivered, and the failure names neither the shebang nor the file. It is also now a **second, independent copy** of the parser's rule: `preprocess` (`src/lang/parser.ts:123`) already computes it and throws it away, and both copies now act — `tjs('#!…\nconsole.log(1)', {dialect:'js'})` emits *one more line* than the input, breaking the line-correspondence the blanking existed to preserve.

**Fix:** have `preprocess` return the stripped hashbang, carry it as its own field (`result.hashbang`) with `code` left clean, and re-prepend it only at file-write sites (`emit.ts`, and `convert.ts` — see M2). Add a library-tier guard: a `src/lang/subset-invariant.test.ts` row (`#!` under `dialect:'js'` and native `.tjs`) plus an assertion that `new Function(tjs('#!…').code)` does not throw. Extend `src/cli/check.test.ts` to cover `tjsx` and `convert`, not just `emit`.

## 🟠 Majors — ship in the same 0.13.2 patch

### M1 · `emit -r` writes THROUGH symlinks in the output directory, clobbering files outside the named tree
`src/cli/commands/emit.ts:159` · *verified* · **data loss reported as success**

With `out/a.js` → `precious/keep.txt`, `tjs emit src -o out -r` overwrote `precious/keep.txt` with transpiled JS and printed `1 emitted, 0 failed`, exit 0. A symlinked output **directory** is also followed: `out/sub` → `../elsewhere` wrote `elsewhere/b.js` while *reporting* `out/sub/b.js`. The read side refuses exactly this escape by construction (`walk.ts`: "descending escapes the tree the user named"); the write side does it silently in the same command. `lstatSync` the destination before `writeFileSync` — unlink the link, or refuse that file loudly. Same for `convert.ts:142`. Pre-existing, but *this* is the diff that decided the tool's symlink policy.

### M2 · `emit` reports success with missing output and exits 0 — the failure-tally fix landed on `convert` only
`src/cli/commands/emit.ts:266` · *verified, reproduced*

Directory of `good.tjs` + syntax-error `bad.tjs` → prints the `✗`, then `2 emitted, 0 failed, 0 skipped`, exit **0**, `bad.js` absent. Same for a failing signature test. Sharper still and not in the original finding: **single-file** `tjs emit bad.tjs -o out.js` also exits 0 with no file written. `emitFile` catches its own error and returns normally whenever `outputPath` is set, so `emitDirectory`'s `catch { failed++ }` is unreachable for the entire practical surface; `emitDirectory` returns `void` so nested tallies never roll up; `emit()` never exits non-zero. `convert.ts` fixed exactly this (issue #24) with a regression test at `convert.test.ts:293`; `emit` has none. **`tjs emit` is the documented production build path (`DOCS-TJS.md:1045`)** — a CI step goes green with a missing module.

**Root cause, worth removing:** `emitDirectory` and `convertDirectory` are ~40-line structural duplicates that have now drifted three ways (recursive-guard placement, tally rollup, exit code). `readEntries` deduped only the 3-line listing — lift the loop into `walk.ts` (`walkTree(dir, {ext, skip, recursive, onFile}) → tally`).

### M3 · `tjs convert` still silently strips the `#!` line — the same defect, one command over
`src/cli/commands/convert.ts:90` · *reproduced this session*

`tjs convert bin.ts -o bin.js` on a `#!/usr/bin/env node` TypeScript source → `✓`, exit 0, output begins `/* tjs <- bin.ts */`. `--emit-tjs` identical, so the TS→TJS→JS chain loses it at the first step and the `transpileToJS` restore never sees it. `convert` is the command the migration docs point TypeScript users at, i.e. the one most likely to meet a real bin script. **The CHANGELOG asserts the hashbang is "now handled in `preprocess`, which every path goes through" — `convert` is a path, and it is not.** Carry it through `fromTS` (both emission modes) or soften the claim.

### M4 · Two false statements ship inside the tarball and to the live playground
`CHANGELOG.md:18`, `CHANGELOG.md:120` · *verified*

- **`perf.test.ts`:** the entry says "no longer prints a ratio". `grep -c 'toFixed(2)}x' src/lang/perf.test.ts` = **19**, and running the file emits `Wrapped chain: 47.92ms (77.33x)` etc. The de-ratio landed on *one lane* (`77c3a97`). `benchmarks.md:18` gives the comparable chain as **2.0×** — a ~29× disagreement, and `guides/benchmarks.md:18` in this same release apologises for exactly that copy-paste having sat in a shipped guide for seven months. `grep -c 'no longer prints a ratio' demo/docs.json` = 1, so it is on tjs-platform.web.app too.
- **Deprecation tense:** `CHANGELOG.md:18` shipped reading "`0.13.0` **will be deprecated on npm**". Registry says it already is (`"Published in error (intended as a release candidate)…"`), as are `0.12.0` and `0.13.0-beta.1`, and the `beta` dist-tag is gone. Review 7 blocked on the *opposite* error (claiming a deprecation that hadn't happened); the fix flipped the sign without adding the missing mechanism — **nothing reads the registry back.**

Pick one for the ratio: de-ratio the 19 sites (or route them through `bin/benchmarks.ts:355`'s DCE-safe `compare()`), or rewrite the bullet to what shipped. Then `bun run docs`.

### M5 · The pre-tag gate is genuinely flaky, and the recorded diagnosis names the wrong lane
`src/cli/port.test.ts:66` · *verified* · **not dismissed as pre-existing**

`awaitListener`'s deadline is **5000 ms** and bun's default test timeout is **5000 ms** — zero headroom, so the apparatus assertion (`apparatus: stranger not listening`) can never fire and the runner pre-empts it with a bare `this test timed out after 5000ms`. That is why the failure recorded in `TODO.md` could not be named. It passes idle (I ran it: 12 pass / 0 fail, 15.9s) and fails 2–5 tests under CPU load. It is in `test:fast` **and CI** (`ci.yml:89`), and it gates tagging via `.githooks/pre-push`.

Separately, `TODO.md:2252` (added in `b61271f`) concludes the flake is the **live-LLM lane** and proposes widening an LLM timeout. The captured full run shows the failure is `port.test.ts` while `models.integration.test.ts` passed. **A wrong diagnosis committed to TODO.md is more durable than no diagnosis** — the next red gate gets waved off as "the flaky LLM lane" while the real defect stands.

Fix: bind the stranger to port 0 and read the port back (hard-coded 18990/18999 can also collide with `listenAsOurs`'s 18700–22699 range); drop `awaitListener` to ~3000 ms and give those tests an explicit `it(..., fn, 15000)`; register the child in `afterEach` cleanup and `await proc.exited`.
