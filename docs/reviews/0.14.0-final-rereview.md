## Blockers

### B-1: Eval scans untrusted source before `maxSourceBytes`, and the literal memos retain what it refused *(verified; security)*
`src/lang/eval.ts:~184`. `maskLiterals(code)` and `masked.match(IDENTIFIER_TOKEN)` run before `checkSourceSize` (around line 210) and outside the `try`. The `scanLiterals`/`memoizedMask` memos (`src/strip-comments.ts:173`, `:507`) are capped by entry count (24 and 16), not by bytes.

- **Measured:** `Eval({ code: "'a',".repeat(2_500_000), maxSourceBytes: 64*1024 })` is refused in about 1.5s and leaves about 316MB of heap after GC. 24 distinct payloads leave about 7.4GB of heap and 15.9GB RSS and take about 36s of CPU. At the base, the same 24 refusals took 29ms with no heap growth.
- **Contract break:** `Eval({ code: 42 })` now throws (`source.split is not a function`), although Eval is documented never to throw.
- **Reach:** `agentRun`/`run` in `functions/src/index.tjs` set `maxSourceBytes: 64*1024` specifically to close this pre-fuel DoS. One 10MB body can OOM a 256MiB instance. Library consumers who pass untrusted code are exposed on publish.
- **Test gap:** the existing size-cap test uses about 550KB and checks only wall time under 1s.

**Fix:** make `checkSourceSize(code, …)` the first statement inside the `try`, and move all params/signature computation after it and inside the `try`. Add a hostile multi-MB literal-heavy test that asserts refusal in a few ms and that the literal memo did not grow (use `clearLiteralCache` plus a size check). As a separate follow-up, give the memos a byte cap.
**Re-review scope:** security + correctness over the eval.ts remediation diff and its tests.

## Majors (must be resolved before GO; same file, same re-review)

### M-1: A context key colliding with a declared `const` breaks the stored function, and the m-1 fix covers `let` only *(verified; correctness + security, merged)*
`src/lang/eval.ts:198-201`. `Eval({ code: 'const total = 9\nreturn total', context: { total: 'X' } })` returns `Cannot redeclare variable 'total' as const`, raised by `constSet` at `src/vm/runtime.ts:3014`. The same call returns 9 on 0.13.11 and 0.13.13, and returns 9 with `let`. The block wrapper only satisfies acorn; the VM scope is function-level.

`functions/src/index.tjs` passes `{...params, ...req.query, ...req.body}` as context, and `public` functions skip auth. So once functions/ upgrades, anyone can break any stored function that declares `const x` by adding `?x=1` to the request. It fails closed (availability/integrity, not escape). CHANGELOG.md:366 and `guides/safe-eval.md:31` both claim shadowing works in general. The only test (`src/safe-eval-doc.test.ts:167`) uses `let`.

**Fix:** do not declare a param for any name the code binds. Parse once with acorn and collect VariableDeclaration, function/arrow param, catch and destructuring binding names. Alternatively, let `const`/`let` shadow an argument binding in the VM. Add const, let and var collision rows. Until the fix lands, narrow the docs.

### M-2: A key referenced only inside a template `${…}` is not declared, so the result silently contains the identifier's name *(verified; correctness; the security-lens minor is merged here)*
`src/lang/eval.ts:184-195`. `Eval({ code: '`hi ${name}`', context: { name: 'bob' } })` returns `'hi name'` with no error, and so does the `return` form. `maskLiterals` blanks template interpolations, so `name` never enters `named`, and the VM's bare-identifier fallback returns the string.

The rc base `1e7ddc2` returned `'hi bob'`, so this is a regression from the rc. 0.13.x was already wrong. It is silent, plausible wrong output in a common usage.

**Fix:** scan identifiers on a view that keeps `${…}` contents (un-mask the interpolation spans from `scanLiterals`, or use acorn). The size bound is unaffected. Add rows to `safe-eval-doc.test.ts` and `literal-blindness.test.ts`.
