## Blockers

### B-1: A Type with a predicate THROWS from `.check` and from param validation during a recursive solve *(verified; regresses from 63012f3)*
`src/lang/emitters/js.ts:2142`

```
Type T { example: { next: T | null, n: 0 }, predicate(x) { return x.n >= 0 } }
T.check({ n: 1, next: null })   // HEAD: TypeError: null is not an object (evaluating 'x.n'); base: true
function sum(list: T) …          // HEAD: same throw escapes; no MonadicError
```

**Cause.** The emitted `x => __match(x, __ex) ? pred(x) : false` assumes the example check guards the predicate. Inside `__kSolve`, `__match` is `__kLook`, and `__kLook` returns an optimistic `true` for a pair it has not evaluated yet. The user predicate therefore runs on `null`. The final verdict would still be sound, but the throw escapes first, which breaks the rule that errors are returned, not thrown.

**What the verifier reproduced.** The main case. The `Pos`/`L` nullable-member variants did not reproduce, which suggests they depend on evaluation order.

**Fix direction.** A predicate must never run on a value whose example match is only assumed. Two options: (a) make the predicate a dependent node that is enqueued only after its example pair is settled true, or (b) treat a throw while the example pair is unsettled as "not yet decided", then defer and re-evaluate. Add both repros as tests. Widen the oracle generator to produce predicate-bearing Types that dereference their argument, used as nullable or union members.

**Re-review scope.** Correctness and blast radius over the remediation diff, with the oracle re-run using the widened generator.

## Majors (all verified; fix before final. They sit in the same diff as B-1, so remediate them together)

### M-1: A negating predicate over a nested `.check` fails OPEN on acyclic data *(security; regresses from base)*
`src/lang/emitters/js.ts:2142`

`Admin {admin:true}`, `NotAdmin = !Admin.check(x)`, `Req {user: NotAdmin}`, `Priv = !Req.check(x)`, evaluated on `{user:{admin:'no'}}`:

| | Base | HEAD |
|---|---|---|
| `Req.check` | true | **false** (valid input rejected; `guest(r: Req)` returns a MonadicError) |
| `Priv.check` | false | **true** (invalid input ACCEPTED) |

**Cause.** An optimistic `true` inside the solve is negated to a `false` that can never be revised, because statuses only move from true to false. It needs no cycle and no recursive Type, only an example that contains any runtime Type.

**Consequence.** The code comment and TODO gap 3 say this case "can over-reject". It can also over-accept, and both need correcting.

**Fix.** Make an opaque user predicate a solver boundary: save and clear solver state, then run the nested `.check` as a fresh exact solve. The alternative is to force any lookup made from inside a predicate to a final status. Add a base-vs-HEAD regression test covering both directions, and add negating predicates to the oracle.

### M-2: A MonadicError satisfies object-shaped params, which disagrees with the dict-default form *(correctness; regresses from base)*
`src/lang/emitters/js.ts:2871`

**What happens.** `f(o: {})`, `f(o: { path: '' })`, `f(o: P)` with `Type P = { x: 0 | undefined }`, and `f(o: {x: 0|undefined})` all run their bodies when passed an upstream MonadicError. At base all four propagated it. `f(o = {x: 0})` still propagates, because only the dict path adds `|| __tjs.isMonadicError(o)`, with the comment "never the options bag". The railway chain is now broken for the most common options-bag shapes.

**Fix.** Apply one rule to every object-shaped check (colon `{…}`, a named object Type, and dict defaults). The recommended rule is that a MonadicError is never an object shape. Add tests for `o: {}` and for an all-optional Type.

### M-3: Solver memory amplification, and the budget bounds work, not memory *(efficiency + security, merged)*
`src/lang/emitters/js.ts:2141`

**Measured.** With `Type T { example: { v: 0.0, kids: [T] } }`:

| Tree | HEAD | Base |
|---|---|---|
| depth 6, branching 10 (1.1M objects) | 1.0 s, **2.0 GB**, accepts | 0.5 s, 0.67 GB |
| depth 5, branching 20 (3.4M objects) | 2.6 s, **4.3 GB**, then rejects on budget | 0.34 s, 0.84 GB |

The security lens (unverified sibling) measured a flat array of N `{id, kids: []}`. At 6e6 elements HEAD takes about 3.3 s and about 4 GB before rejecting. Base rejected early at its 1e6 budget.

**Cause.**
- Each data object gets 3–5 nodes: the ref marker, the Type, the example, and the float leaf. Each node carries a `par` Set and a WeakMap entry.
- `__kBudget = 1e7` counts evaluations. Nodes are created on lookup, so memory is spent before the budget is checked.
- The budget went up from 1e6 to 1e7.

**Why it matters.** It is a memory-amplification DoS for any server function whose parameter is a recursive Type. HTTP body limits lower the ceiling but do not remove it.

**Fix.**
- Collapse the delegating layers so there is one node per (value, example) pair.
- Match directly any sub-example that cannot reach a ref (`if(!__kObj(t)||!__kRec(t))return __m0(x,t)`).
- Store a single parent inline instead of a Set per node.
- Charge node creation against the budget and size it to hundreds of MB worst case.
- Add a guard that pins peak memory at the budget boundary.
