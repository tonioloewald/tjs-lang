## Blockers

### B1. Compiled regex retained memory is never charged to the live-heap ceiling (confirmed)
**Where:** `src/vm/regex.ts:729` (`compileRegex` keeps `mark: new Int32Array(stateBase[prog.length]).fill(-1)` and prog/liveOf/stateBase on a non-enumerable PROGRAM symbol), and `src/vm/runtime.ts` evaluateExpr `'regex'` (around line 3909), which compiles on every evaluation and never calls `allocate()`.

**Failure:**
- Under `{ fuel: 100000, maxHeapBytes: 8MB }`, running `while (i < 1000) rs.push(/(?:(?:…(?:a)?…)?)?/)` (15 nested optionals, 163,839 states) returns `{n:1000}` after 506 fuel.
- RSS grows by about 690 MB. At 3000 iterations it grows by about 2 GB.
- Holding `/a{10000}/` 1000 times leaks about 635 MB through prog alone.
- reconcileHeap sees only six small enumerable keys.

This breaks the `docs/vm-budgets.md` invariant that "every byte outliving its step is charged where it becomes reachable".

**Fix:**
- Do not retain `mark`. Allocate it per operation; threadBytes already budgets stateBase×4 per op.
- Charge the immutable program's retained size (instructions × bytes, liveOf, stateBase) through `allocate()` when a regex node is evaluated.
- Teach the heap measurement and reconcile walk to size a GuestRegex by its compiled program.
- Add heap-reconcile/vm-budgets rows that hold many compiled regexes.

**Re-review scope:** correctness + security over regex.ts and runtime.ts heap accounting (the remediation diff only).

## Majors (confirmed, non-blocking but fix before final)

### M1. predicate-regex `hits()` advances one code unit past an empty match under `u`, so it loops until fuel runs out (confirmed)
**Where:** `src/lang/predicate-regex.ts:44-52`.

**Failure:**
- `from = hit.end + 1` lands on a trail surrogate, and execRegex backs up to the lead.
- `s.replace(/(?:)/gu, fn)` and `[...s.matchAll(/(?:)/gu)]` on `'😀'` throw PredicateFuelExhausted. Native returns `'-😀-'` and 2.
- The string-replacer path through `allMatches` is correct. The two copies have already drifted.

The fix is to delete `hits()` and reuse string-methods' `allMatches`/`advance`. Add differential rows for a `u` empty match with a function replacer and with matchAll over astral input.

### M2. Transpile/verify-time regex compile has a per-regex cap but no per-source budget (confirmed)
**Where:** `src/vm/regex.ts:49` (MAX_REGEX_COMPILE_WORK = 1e6, unmetered default), `predicate.ts:366/726`, `predicate-schema.ts:96`, `emitters/ast.ts:503`.

**Measured cost:**
- `/(?:(?:){10000}){99}/` takes about 20 ms to compile.
- 100 of these in 3.3 KB of source: verifyPredicate 1.2 s, compilePredicate 2.3 s, compilePredicateSchema 3.5 s. The schema path compiles each literal three times.
- An AJS transpile of 4 KB takes 1.2 s.

This undermines `maxSourceBytes` as an admission cap, and `$predicate` schemas arrive as data. Growth is linear, so this is a large constant factor, not a hang.

**Fix:**
- Add a shared per-source compile budget, or lower the per-regex cap.
- Compile once per literal and hand the compiled regex from verify to the lowering step.
- Skip `mark` on validate-only compiles.
- Fix the regex.ts and vm-budgets.md "terminates promptly" wording, or make it true per source.

- **m4 (blast-radius, unverified).** HostRegex re-implements the function-replacer, match-array and global-iteration logic beside string-methods. This is a second copy with no differential test, and it is the structural cause of M1.
- **n1 (correctness/blast-radius, unverified).** DOCS-AJS documents only the `{10000}` count cap, but the 20k-instruction program cap refuses `\w{0,5000}` and `.{0,10000}`. The CSS perf baseline also disagrees: CHANGELOG says ~0.7 ms and `src/css/perf.bench.test.ts:7` says ~0.1 ms.
