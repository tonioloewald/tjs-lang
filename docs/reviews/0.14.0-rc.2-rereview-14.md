## Blockers

### B1. The builder `.validate` door admits one object and validates against another, so guest regex reaches the host engine (correctness + security, CONFIRMED, merged)

`src/vm/runtime.ts:2786`. `methodGate` calls `admitGuestSchema(receiver)`, which reads `receiver.schema`. tosijs-schema's `validate` validates against the schema `e` captured in its **closure**. The guest can make the two differ for three reasons:

1. `kindOf` uses the library's duck-typed `isBuilder`: a `validate` function plus `'schema' in e`. Guest code can read `b.validate` as a value, and an object spread copies the enumerable brand symbol.
2. `meta` is typed `'schema'`, and `checkArgs` admits `convertExampleToSchema(arg)`, which is a harmless `properties` schema. The library then merges the **raw** keywords (`{...r, ...e, ...r}`), so `pattern` ends up in the closure.
3. Neither the static `SCHEMA_SITES` scan nor the generated corpus (whose doors are `isValid`/`filter` only) sees a dynamic `receiver[method]()` call.

Reproduction, AgentVM and vm-ast, with `p='^(a+)+$'` and `s='a'*27+'!'`:
```js
const b = Schema.email.meta({ pattern: [p] })
const o = { schema: {}, validate: b.validate }
return { v: o.validate(s) }      // also: { ...b, schema: { type: 'string' } }.validate(s)
```
Under Bun/JSC this took about 380ms at fuel 50 and timeoutMs 100, with fuelUsed about 1. The instrumented RegExp recorded `new RegExp('^(a+)+$')`. Under Node/V8, 31 characters took **51s**, growing about 4x per 2 characters. The control, `b.validate(s)` called directly, is correctly refused.

**Required fix:**
- Never call a guest-reachable builder closure. Implement builder `.validate` in the VM as admit-then-`validate(x, snapshot)` on exactly the object that was admitted.
- Recognise builders only through a VM-created WeakSet, not by duck typing, or refuse to read function-valued members of builders.
- Give each construction door an argument-specific admission: `meta` admits its raw argument as a keyword set; `union`/`tuple` admit each element; `object` admits each member.
- Add a builder-door and builder-supplier dimension to the generated corpus: `meta`, `union`, `tuple`, builder `.validate`, stolen-validate, and spread builder.
- Run the corpus under node as well as bun, because JSC's backtracking limit hides the blow-up.

**Re-review scope:** security plus correctness over the remediation diff. Include every value-to-host-function path out of the `Schema` namespace, and re-run the corpus under node.

## Majors (confirmed; not individually release-blocking, but this release is already blocked, so fix them in the same remediation)

### M1. The core `llmPredict` sends `options.responseFormat` to the capability unadmitted (correctness, CONFIRMED)
`src/vm/runtime.ts:~5993` passes `resolveValue(options)` straight to `ctx.capabilities.llm.predict`. `admitResponseFormat` exists only in `batteries.ts`, so one atom got the fix and its sibling did not. The atom left unfixed is the documented path: `guides/examples/ajs/llm-*.md` and DOCS-AJS both use `llmPredict({ prompt, options: { responseFormat } })`. `Schema.response` also does not re-admit the builder it wraps. The CHANGELOG says LLM responseFormat schemas are admitted, which is untrue for this atom. **Fix:** move `admitResponseFormat` next to `admitGuestSchema` in runtime.ts, call it from `llmPredict` and from both battery atoms, and add a corpus row per LLM atom.

### M2. `admitResponseFormat` admits only `json_schema.schema` and lets every other shape through; `tools` is not admitted at all (security, CONFIRMED)
`src/vm/atoms/batteries.ts:11`. `{type:'json_object', schema:{pattern:…}}` is a shape llama.cpp compiles to a grammar, and it passes unadmitted. So does a top-level `schema`, and so does `tools[].function.parameters`. The commit's own rationale (a grammar compiler working outside every budget) covers all of them. **Fix:** allowlist the shape and refuse anything else (`{type:'json_schema', json_schema:{name,strict,schema}}` or `{type:'json_object'}` with no other keys), and admit every schema inside `tools`. Note that the behavioural corpus cannot see these doors, because they compile nothing on the host. **Re-review scope:** security over the batteries diff.

### M3. Validation work is schema size times data size, but it is charged additively (correctness, CONFIRMED; completeness gap reproduced the same class)
`src/vm/runtime.ts:2551/2562`. The `isValid`/builder-`validate` bound is `TREE_ARGS(1)`, and the `filter` bound is `2*treeBytes(data)`, which ignores the schema. Measured with an `anyOf` of 3,300 `const` branches (admitted under the 10k-node cap) against a 97x97 array: **about 630ms of synchronous host time for about 63 fuel**, roughly 10ms per fuel and about 1000x off the cost invariant. 10 calls took 6.4s for 673 fuel. `filter`/`oneOf` took 1.33s and overran timeoutMs 1000, because the call cannot be interrupted. The completeness probe measured 13.8s in one `filter` call over 100k objects. The same class applies to the `return`-step schemaFilter and to `enum.includes`. **Fix:** have `admitGuestSchema` return its node count and charge `nodes × data-tree size` through `allocate`/fuel before the call, or lower the cap until the product fits the timeout ratio. Add cost-invariant rows for anyOf fan-out times a large array, for each door.

### M4. The guest-schema admission walk is not charged and is slower in this diff (efficiency, CONFIRMED)
`src/vm/runtime.ts:2852-2985`. Test: 2,000 calls of `filter({}, 9k-property schema)`. Time went from 4.6s to 6.7s (verifier's measurement) with the **same** fuel. The verifier measured about 6ms per fuel against about 3µs per fuel for a plain loop. Causes:
- `GUEST_SCHEMA_KEYWORDS` and its helper closures are rebuilt on every call.
- `plainObject` copies every node.
- Path strings are built on the success path.
- `checkArgs` converts the example, and the method body converts it again.

The uncharged walk predates this diff, but per project policy that is not a reason to defer it. **Fix:** charge `nodes × per-node` cost; hoist the table and helpers to module scope; build paths lazily; convert the example once. Add a large-schema cost-invariant row. (Fix together with M3, since both concern fuel tracking work at the schema doors.)
