## Blocker

### B-1. The paren-depth guard and the transform read different lexical views, so the quadratic recursion comes back under the 64KB cap (confirmed; correctness + security)
- **Where:** `src/lang/parser-params.ts:224` (`assertParenDepth`), which is called at `parser.ts:499` and `parser-agent.ts:131`. The recursion is at `parser-params.ts:949`, and `processParamString` reaches it through line 1601.
- **Mechanism:** the guard counts `(` over `maskLiterals(source)`. That view blanks whole template literals, `${…}` included; `maskLiterals('`a${(1)}b`')` returns only spaces. The transform goes back to its normal state inside `${` and recurses once per nested group. There is a second disagreement: after `}`, the masker treats `/` as the start of a regex while the transform's `isRegexContext` (line 468) treats it as division. For `if (1) {} /((((…))))/`, the guard sees 1 paren and the transform recurses 8000 deep, and the run then succeeds.
- **Measured on HEAD:**
  - `Eval({ code: 'return `${' + '('.repeat(n) + '1' + ')'.repeat(n) + '}`', fuel: 10, timeoutMs: 100 })` takes 63ms at n=1000, 825ms at n=4000, 3.6s at n=8000 (16KB), 20.6s at n=20000 and about 42–50s at 60–64KB, then fails with `Maximum call stack size exceeded` and fuelUsed 10.
  - `vm.run(source)` and `tjs()` behave the same way.
  - The functions `agentRun`/`run` endpoints (`functions/src/index.tjs:146, 255`) pass caller code to Eval under the 64KB cap, so any signed-in account can tie up an instance for about 40s per request.
- **It also refutes a documented claim:** the CHANGELOG (~line 78) and the `MAX_PAREN_DEPTH`/`DEFAULT_MAX_SOURCE_BYTES` docstrings say about 105ms at the cap.
- **Fix direction:** put the depth limit where the recursion happens. Thread `depth` through `transformParenExpressions`' ctx and `processParamString`, and throw the same SyntaxError at line 949 when depth exceeds `MAX_PAREN_DEPTH`. `assertParenDepth` can stay as the cheap early refusal, but it cannot be the only control. Better still, make the recursion iterative so that depth no longer matters, which also resolves m-1 below.
- **Tests:** add SOURCES rows in `src/admission.test.ts` for both shapes: parens nested 20000 deep inside a template interpolation, and a regex after `}`. Assert the refusal message, not only a time bound. As a rule, add a row for every context `maskLiterals` blanks that some later pass still walks.
- **Re-review scope:** security + efficiency + correctness over the remediation diff. Include an adversarial pass that asks, for every context `maskLiterals` blanks, whether any recursive preprocess pass (the given-transform fixpoint, `processParamString`) still walks it or bases its bound on `maskLiterals`.

## Majors (confirmed; fix before release)

### M-1. Run-level `timeoutMs: 0` silently changed from "expired" to "no wall-clock limit" (`src/vm/vm.ts:383`)
- `timerMs(0)` now returns `undefined`, so no run timer is armed. At `ff331e9`, `vm.run(ast, {}, { fuel: 100, timeoutMs: 0 })` with a slow fetch timed out after 3ms. On HEAD it runs 304ms with no timeout error.
- "0 disables" was documented only for the per-atom `timeoutOverrides`. The CHANGELOG mentions only `Infinity`, and no test covers run-level 0.
- This fails open in a module whose rule is "refused rather than defaulted". A host that passes its remaining deadline will pass 0 once the deadline is spent, and gets an unlimited run.
- **Fix:** decide which meaning is intended and pin it with a test. The recommended choice is that run-level 0 means already expired. If the new meaning stays, document it in the vm.run option comment and the CHANGELOG as a behaviour change.

### M-2. No test fails when the vm.run(source) cap is removed; the re-review-4 B-1 fix is unpinned (`src/admission.test.ts:52`)
- Mutation test: changing `options.maxSourceBytes ?? DEFAULT_MAX_SOURCE_BYTES` to `?? Infinity` left 759 tests passing and 0 failing.
- The SOURCE_ENTRIES rows assert only wall-clock time and swallow exceptions. `maxSourceBytes` is never exercised with a real value; it appears only as `'x'` in the invalid-options table.
- **Fix:** every SOURCE_ENTRIES row should return and assert its refusal reason. The 1MB vm.run row must match `/over the \d+-byte limit/`. Add a test that `maxSourceBytes` is honored: 1KB refuses a 2KB source, and a higher value admits it.
