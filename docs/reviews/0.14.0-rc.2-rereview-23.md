## Blocking

### B1. The `vm.run(source)` and `createAgent` paths transpile without the VM's atoms (major, confirmed by 2 lenses)

- **Where:** `src/vm/vm.ts:303`, where `transpileImpl(astOrToken)` is called with no options although the VM holds `this.atoms`. The same gap is in `createAgent` (`src/lang/core.ts:121`, `src/lang/index.ts:446`), in `demo/src/playground.ts:857` (`transpile(code)`, which runs on a VM with battery atoms), in `site/entry.ts:38` (which passes only `maxSourceBytes`), in the `ajs` tag, and in the playground's `code.transpile` capability.
- **What goes wrong.** `atomInputs` (`src/lang/emitters/ast.ts` ~2320) reads `ctx.options.atoms` and falls back to `CORE_ATOM_INPUTS`. Two failures follow, both reproduced at HEAD:
  1. **A false rejection, newly introduced by this diff.** `new AgentVM({ httpFetch: defineAtom('httpFetch', s.object({ url: s.string, cache: s.number.optional }), …) }).run("…httpFetch({ url:'x', cache:5 })…")` throws `'httpFetch' has no input 'cache'`. The same program ran before this round. The breakage reaches consumers when they upgrade.
  2. **The defect this round exists to prevent is still there.** `new AgentVM({ greet }).run("…greet({ nam: 'x' })…")` runs with no error and the input undefined. The same applies to battery atoms in our own playground: `llmPredictBattery({ promt })` is not refused.
- **Why it blocks:** The user's direction is that "it's AJS's job to prevent you from writing code with bad parameters." On every transpile path that has a VM in hand, the transpiler either checks against the wrong contract or checks nothing.
- **Fix.** Pass `{ atoms: this.atoms }` at `vm.ts:303`. Pass `vm.atoms` in `createAgent`, `demo/src/playground.ts` and `site/entry.ts`, and check whether `Eval`/`SafeFunction` and the `ajs` tag can receive the VM's atoms too.
  - Add `call-shape.test.ts` rows for (a) a host atom overriding a core name with a wider schema, run via `vm.run(source)`, which should be accepted, and (b) a misspelled host-atom input via `vm.run(source)` and via `createAgent`, which should be refused.
  - **Cycle note for the remediating agent:** the underlying question is structural. Every transpile entry point that runs beside a known VM has to reach the same atom table. Today that depends on each caller remembering an option. Consider making the atom set a required or derived input at those entry points rather than adding the option one call site at a time.
  - Re-review scope: correctness and blast-radius over the remediation diff only.

## Plan (round 19, filed before acting)

**Underlying problem:** the atom contract the transpiler checks against is an OPTION each caller
must remember to pass. Every entry point that holds a VM forgot it, so it checked against the
wrong table (a false rejection) or against nothing (a silent run). This is wiring, not a new
misreading of schemas: the rule itself (round 18) is unchanged.

**Fix:** one shape for "which atoms is this code for":
- every entry point that runs beside a VM derives it from that VM: `vm.run(source)`,
  `createAgent(source, vm)`, `Eval`/`SafeFunction`, the playground and the doc site. Each passes
  `vm.atoms`, found by grepping every transpile call that has a VM in scope.
- one `contractOf(schema)` in `core-atom-inputs.ts`, used by both the emitter and the table test.
  It unwraps with `isBuilder` (#58), applies `required` whenever it is present, and applies the
  unknown-key check only to a closed schema.
- rows, each via `vm.run(source)` and `createAgent`:
  - a host override with a wider schema is accepted;
  - a misspelled host input is refused;
  - an open schema missing a required input is refused.
- `REFUSED_AT_TRANSPILE` gets a message regex per row.
- the CHANGELOG adds the persisted-positional-AST sentence.
