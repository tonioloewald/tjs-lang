## Blockers (all adversarially verified)

### B-1. Successful regex scans in `extractReturnTypeValue` are never metered (correctness + efficiency)
`src/lang/parser-params.ts:1442`, `src/strip-comments.ts:84-132`

- **Defect.** `findRegexEnd(source, i, regexMemo)` runs at every `/` *before* the `isRegexStart` check. When that check is false, the `/` is not consumed. `RegexScanMemo` records only failures, so a scan that succeeds is repeated from every candidate. The only charge is `charge(work, i - start)`; the scan's own steps are never billed.
- **Repro 1** (accepted, quadratic): `'function f() {\nlet z = [' + '(a): [x/] => 1,'.repeat(n/15) + '/]\n}'` took 44 / 128 / 489ms at 15K / 30K / 60K. An instrumented count gave 15M / 60M / 240M scan steps (about 4000× n), while the charged total was 2× n. The control, which ends in `1]` instead of `/]`, ran in 3 / 4 / 10ms.
- **Repro 2** (refused, but only after n^1.5 uncharged work): `'function f(): (' + 'a/[a'.repeat(N) + ']/)\n'` took about 330-355ms at 60KB, 923ms at 120KB and 2768ms at 240KB (`maxSourceBytes` can be raised).
- **Impact.** This refutes both the "refused at WORK_PER_CHAR × n" invariant and the "~114ms worst at the cap" claim (CHANGELOG.md:94, src/lang/eval.ts:184). It stays under the 1500ms BOUND_MS, so no test catches it.
- **Fix.** Pass `work` into `findRegexEnd`, or return the scanned length and charge it. Check `isRegexStart` (charged, or tracked incrementally as a sigTail) *before* scanning. Optionally memoize successes too, since the future of a (position, state) pair is deterministic either way. Add both shapes to `admission.test.ts`. Add an invariant test: instrumented real scan steps ≤ `work.used` × a small constant. Add a scaling assertion: time at CAP vs CAP/4 < ~5×.

### B-2. Nested destructured parameter patterns: unmetered, no depth bound, 14-28s per request (security)
`src/lang/parser-params.ts:2103` (`processDestructuredObjectParams`), `:2184` (`processObjectLiteralValue`), `:2235` (`processArrayLiteralValue`)

- **Defect.** The recursion runs once per nesting level. Each level does a slice, a trim, `splitParameters` and anchored `[\s\S]*` regexes over the remaining pattern, which is O(depth × length). There is no `charge()` call; the ctx type has no `work` field. `MAX_PAREN_DEPTH` does not count `{` or `[`.
- **Repro (preprocess).** `function main({a: {a: … b: 1 …}}) {}` took 120 / 478 / 2698ms at depth 1K / 2K / 4K, and all three were **accepted**.
- **Repro (public API).** `vm.run(source, {}, {fuel: 5, timeoutMs: 50})` took 14.3s at 40KB. The reporter measured 27.7s at 65KB, which then failed with "Maximum call stack size exceeded". The refusal comes from stack exhaustion after the work is done. `timeoutMs` cannot help because transpilation is synchronous and runs first. Arrow-parameter and `[{a: [` variants take 21-22s.
- **Fix.** Thread `work` through all three functions and `splitParameters`, and charge every recursion and scan. Bound `{` / `[` nesting in parameter patterns so refusal happens before stack exhaustion. Structurally, walk the pattern once rather than re-slicing and re-matching per level. Add admission rows for `{a: `, `[{a: ` and `{a: [` nesting in function, method and arrow parameter position that assert *refusal*, not only "< N ms". Correct the "all scanning is metered" comments in parser-agent.ts and eval.ts.

### B-3. `RE_FUNCTION_HEAD` polynomial backtracking, invisible to the meter (security)
`src/lang/parser-params.ts:1390`: `/function\s*\*?(?:\s+(ID))?\s*\(/y`

- **Defect.** The regex has three adjacent, overlapping `\s` quantifiers, so it is O(n²) when no `(` follows. `matchAt` runs it at every `function`, and `charge()` cannot see regex-engine steps.
- **Repro.** The regex alone took 173 / 693 / 2764ms at 15K / 30K / 60K spaces. `preprocessAgentSource('function main() {}\nlet function' + ' '.repeat(65496) + '1')` (65,528 bytes) took 3,307ms, and the budget did not refuse it. The reporter measured 3.3s through `vm.run` and `Eval`. Newlines and tabs trigger it too.
- **Why nothing caught it.** The trigger is a single keyword plus a run, not a repeated pair, so the pair grid misses it. `self-redos.test.ts` flags only star-height ≥ 2, and this pattern is star-height 1.
- **Fix.** Hand-scan the head, or emulate atomic groups with `(?=(\s*))\1`. Audit every sticky regex reachable from `preprocessAgentSource`: RE_METHOD_HEAD, RE_CLASS_NAME, RE_KEYWORD_VALUE and the `^(\w+)\s*\?\s*:\s*(.+)$` family. Extend `self-redos.test.ts` to flag adjacent unbounded quantifiers over intersecting character sets. Add an admission row of "each keyword/anchor + a 60KB run of each whitespace class".

### B-4. acorn is quadratic in block nesting, and only paren depth is bounded (correctness)
`src/lang/parser-agent.ts:165`

- **Defect.** `parseAgentSource` hands the preprocessed source straight to `acorn.parse`. `{` nesting is unbounded, and the TransformWork budget does not cover acorn.
- **Repro.** `'function f() {\n' + '{a;'.repeat(n) + '\n}'`: acorn took 49 / 170 / 695ms and Eval({fuel:10, timeoutMs:20}) took 127 / 458 / **1876ms** at 15K / 30K / 60K. Each run ends in "Unexpected token". `{a\n` and `{f(a)\n` take about 810-860ms, some ending in a stack overflow. 1876ms exceeds `admission.test.ts` BOUND_MS (1500) and refutes "~114ms worst" in eval.ts:184 and the CHANGELOG. The acorn cost predates this diff, but it is in the class the brief names, TODO.md does not track it, and "predates" is not a reason to defer.
- **Fix.** Add one linear pass over the literal-masked view that bounds the depth of all of `{`, `[` and `(` before acorn. Measure the real-corpus maximum for braces; 64-256 is likely generous. That pass also removes the stack-overflow outcomes. Add `{a;`, `{a\n` and `{f(a)\n` rows to SOURCES, run through **every** entry (Eval, SafeFunction, vm.run, ajs``), not only the preprocessor. Then restate the worst-case figure.
