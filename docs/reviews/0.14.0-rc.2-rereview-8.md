## Blockers (all confirmed)

### B1. The zero-width closure is uncharged and copies the full capture array, so fuel does not track time
`src/vm/regex.ts` ~651–713 (`add()`, `charge(clist.length + 1)`).
- Reported by the correctness, efficiency and security lenses; deduplicated here.
- **Cause:** `add()` walks up to the whole program (MAX_REGEX_PROGRAM = 20k instructions) and runs `c.slice()` over `nCaps = (groups+1)*2 + regs` slots at every `save`, `mark` and `reset`. None of that is charged. The only charge is one flat step per thread per input position.
- **Measured:**
  - `s.match(/()…×5000/g)` on 300 characters: 14.7 s for 2 fuel.
  - `(?:(a)|…×1500)*b` on 1000 characters with fuel 100: 6.6 s and no error. That is 218 ms per fuel, against the 10 ms per fuel the timeout model assumes.
  - `/(?:(a)|(aa)){0,1500}$/` on 2001 characters: 14.2 s and about 1.1 GB RSS, none of it counted against `maxHeapBytes`.
- **Impact:** the call is synchronous, so the timeout cannot preempt it. This breaks `cost-invariant.test.ts` (fuel must be at least c × work) and the CHANGELOG/README claims "linear-time Pike VM, fuel per step" and "no pattern can hang a run".
- **Fix:**
  - Charge every `add()` visit, and charge each caps copy in proportion to its width. Better, remove the copy cost structurally with copy-on-write or persistent capture vectors.
  - Cap `groups + regs` at compile time.
  - Count thread capture arrays against the heap meter.
  - Add cost-invariant rows that check wall-ms per fuel for many-groups patterns on growing inputs.

### B2. An empty quantified group compiles in an uncharged, uncapped host loop
`src/vm/regex.ts` ~469/486 (`for (k < node.min) iteration(false)`).
- Reported by the correctness and security lenses; deduplicated here.
- **Cause:** with an empty body, each iteration emits no instructions, so `prog.length` never grows and the MAX_REGEX_PROGRAM check never fires. `parseQuantifier` accepts any count. Compilation is never charged, either at the `regex` node (runtime.ts:3909) or in `toRegex`.
- **Measured:**
  - `(?:){1e8}`: about 0.8–1.2 s.
  - `/(?:){300000000}/` with fuel 1 and a 50 ms timeout: 3.3 s, 0.34 fuel, no error.
  - Nested `(?:(?:){1000}){1000000}`: 7.9 s.
- **Impact:** `(?:){9007199254740991}` is a 25-byte payload that hangs the host. It is reachable from guest-built strings and from a regex literal node in any submitted AST, before any budget applies.
- **Fix:**
  - Refuse `{n}`/`{n,m}` counts above a cap at parse time.
  - Bound the loop by count as well as by program size.
  - Charge compilation in proportion to source length plus program size.
  - Add `(?:){1e12}` and nested-empty rows to `regex.test.ts` and `malicious-actor.test.ts`.

### B3. A character-class test costs time in proportion to the class size but is charged as one step
`src/vm/regex.ts` (parseClass → `ranges.some(...)`; with the `i` flag, `caseVariants(x)` allocations).
- Reported by the security lens.
- **Cause:** the whole class is a single `char` instruction, so it counts as 1 toward MAX_REGEX_PROGRAM no matter how large it is.
- **Measured:**
  - `'b'.repeat(20000).search('[' + 'a'.repeat(400000) + ']')`: 20.6 s for about 0.92 fuel with a 500 ms timeout.
  - The verifier reproduced 1.3 s with smaller inputs.
- **Fix:**
  - Compile classes into a sorted, case-folded range table and test with binary search, or cap class size and count it toward the program cap.
  - Charge accordingly.
  - Add a wide-class hostile test.
  - Correct the regex.ts header and CHANGELOG claims.

## Majors (all confirmed; fix in this cycle, they are not deferrable to the next release)

- **M1 (correctness). Lazy quantifiers inside `+`/`*` give different results than JS** (`src/vm/regex.ts` ~663).
  - Threads are deduplicated by pc only. A thread that fails the `progress` check still marks that pc, so a lower-priority thread whose register would pass gets dropped.
  - Examples: `/(?:a*?)+/` on `'aa'` gives native `'aa'`, ours `'a'`. The same happens for `/(a*?)+/`, `/(?:.*?)+/` and `/(?:x*?a*?)+/`. Results are silently wrong in replace, split and match.
  - Fix: do not mark the pc when `progress` fails, or include the register in the dedup key. Add a random differential fuzz over lazy and nested quantifiers.
  - Re-check linearity after the change, because the dedup key interacts with B1.
- **M2 (correctness). The ASI-guard exemption `isBareControlHeader` only recognises single-line headers** (`src/lang/parser-transforms.ts:1120`, used at line 1284).
  - (a) `if (a &&\n b)\n [r] = [1]`: the inserted `;` becomes the if-body, so the assignment runs unconditionally. This is a silent miscompile of valid JS.
  - (b) A `label:` before `for` throws "i is not defined".
  - (c) `for await` throws "x is not defined".
  - These are sibling sites of the defect this commit says it fixed.
  - Fix: decide header end from the parenthesis structure on the masked view, and allow `label:` and `for await`. Add literal-blindness and subset-invariant rows.
  - Re-review: correctness + blast-radius over the ASI diff.
- **M3 (efficiency/security). Each execRegex call does O(program) setup that is never charged** (`src/vm/regex.ts:626/634`).
  - `Int32Array(prog.length).fill(-1)` plus a fresh caps array runs on every call. `split`, and global replace/match on patterns that can match empty, call execRegex once per input position.
  - Measured: `'a'.repeat(1e5).split(/zqqq…19000/)` takes 330 ms for the same fuel as `split(/z/)`.
  - Fix: reuse the mark array with a monotonic generation counter. Charge `prog.length` if any per-call work remains. Consider a single unanchored scan for `split`.
- **M4 (security). `substitute()` computes the output length over subs × pieces before any charge** (`src/vm/string-methods.ts` ~171–180).
  - `parseReplacement` and the nested length loop are uncharged and run before `m.alloc`.
  - Measured: `'a'.repeat(5000).replaceAll('a', '$&'.repeat(500000))` took 3.5–4.2 s for about 16–117 fuel, ignoring a 100 ms timeout, before the correct heap refusal.
  - Fix: check the running length against heap headroom inside the loop, or charge one step per (sub, piece). Add a malicious-actor row.
- **M5 (blast-radius/security). Predicates still run regexes on the host's backtracking engine** (`src/lang/predicate.ts:358–372`, comment at line 26).
  - `verifyPredicate('…/a*a*c/.test(s)…')` returns `safe:true`. `compilePredicate` and `tjs-lang/schema` `validate` with a `$predicate` take about 1.6 s on 3000 characters and about 13 s on 6000.
  - `$predicate` is meant to travel as data, so a schema author can stall the validator.
  - The CHANGELOG's "ReDoS is now ordinary work" reads as package-wide but covers the VM only. The predicate.ts:26 comment ("the verifier and the VM reject the same shapes") is now false.
  - The polynomial gap predates this commit. That is not a reason to defer: the release notes now promise more than the code delivers.
  - Fix: lower predicate regex literals to `compileRegex`/`execRegex`, charged against the predicate's fuel, and make the verifier refuse what the engine refuses. Otherwise, narrow the CHANGELOG claim, add `/a*a*c/` as a tracked known miss in the redos-lint corpus, and file a keep-decision card.
