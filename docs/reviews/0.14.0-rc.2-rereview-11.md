## Blockers

### B1. A verified predicate compiles a guest string pattern on the host regex engine, unmetered (confirmed)
- **Where:** `src/lang/predicate.ts`, around lines 131–185 (`PURE_INSTANCE_METHODS`), around 386 (the Literal screen) and around 738 (`lowerRegexLiterals`).
- **Defect:** The verifier screens only regex **literals**, and `lowerRegexLiterals` rewrites only literals into `__rx(k)`. `match`, `search` and `matchAll` (and `replace`) count as pure whatever their argument is. A string argument therefore reaches native `String.prototype.match`/`search`, which runs `new RegExp(str)` outside the per-source `RegexCompiler` and outside the run's fuel and meters.
- **Repro:** `verifyPredicate("function p(s) { return s.match('(a+)+$') != null }")` returns `safe: true` with no diagnostics. With `compilePredicate(..., { fuel: 1000 })`, the input `'a'×n + '!'` took 13.7, 52.9 and 214.7ms for n = 20, 22 and 24 under Bun from source. Under node against `dist/tjs-lang.js` it took 199ms at n = 24 and 794ms at n = 26, so around 34 characters means minutes. Fuel never fires. `createPredicateEvaluator` and the `$predicate` / `tjs-lang/schema` path also accept this source instead of failing closed.
- **Promise broken:** the predicate verifier fails closed on ReDoS, and a verified predicate halts within its fuel (the `redos-lint` guardrail). This bug predates this diff. Per project rules that is not a reason to defer it.
- **Fix:** Send a non-regex argument to `.match`, `.search` or `.matchAll` (and check `.replace`/`.split`/`.replaceAll`) through a pure runtime helper. The helper should compile `String(arg)` with `compileRegex` against the predicate's meters, the same way `prepare()` in `string-methods.ts` does. The alternative is for the verifier to refuse those methods unless the argument is a regex literal. Add a `redos-lint` row that fails today: the string-pattern `(a+)+$` predicate at fuel 1000 must finish, or fail promptly, on a 40-character input. **Re-review scope:** correctness, security and blast radius over the predicate compile and lowering diff.

## Majors (do not block on their own, but schedule them in this cycle)

### M1. Regex parse memory is charged at a flat per-character rate, and class escapes allocate about 10 times that (confirmed)
- **Where:** `src/vm/regex.ts:814`, `alloc(64 + source.length * PARSE_BYTES_PER_CHAR)`, and `parseClass` / `classEscape` / `complement`.
- **Defect:** Each `\S`, `\D` or `\W` inside a class allocates fresh range tuples through `complement()`, about 11 for `\S`. They stay alive in the unmerged `ranges` array until `charNode` normalizes them. That is roughly 300 bytes or more per source character against the 64 that are charged.
- **Repro:** A guest string pattern `'[' + '\\S'.repeat(450000) + ']'` passed to transpiled `function f(p: '') { 'x'.match(p) ... }` under the **default** `maxHeapBytes` (64MB) was charged about 57.6MB and admitted, and peak RSS grew by 566–636MB. This breaks I1 ("nothing allocates before it is charged") on an ordinary guest call, and the code comment's claim of a constant cost per character is false. The transpile-time and predicate `RegexCompiler` paths have no memory meter at all.
- **Fix:** Charge class contents as they are built: charge each escape's range count through `alloc` before pushing it, or normalize incrementally so the array has a bound per character. Derive `PARSE_BYTES_PER_CHAR` from a measured worst case, and add a `vm-budgets` row that measures RSS against the default ceiling. **Re-review scope:** correctness and efficiency over `regex.ts` parse and compile.

## Remediation plan (round 7), written before acting

**Root cause.** Regex is reachable through an OPEN set of doors, and each is costed by its own
meter resting on its own assumption. Every round has found one more of either:

- doors: a literal; a string pattern to a method (VM, then predicates); transpile time; verify
  time; a helper context;
- assumptions: work per step only; "this context has a parent"; a flat parse cost per character.

**Structural changes, not patches:**

1. **A closed set of doors, enforced by parsing.** Every regex compile in `src` goes through a
   metered entry (`compileRegex` called with both meters, or `RegexCompiler`), and a guardrail
   test parses `src` and fails on any other call site, and on any `RegExp` construction reachable
   from guest or predicate input. Predicates become a closed surface: the verifier refuses a
   pattern argument to `match`/`search`/`matchAll` unless it is a regex literal (which is lowered
   onto the engine), so a string can never reach the host engine. (`replace`/`split`/`replaceAll`
   take a string literally and compile nothing.)
2. **Charge at each allocation, never by a model.** The regex parser charges every allocation it
   makes (nodes, class range tables, unmerged escapes) through `alloc` as it makes it.
   `PARSE_BYTES_PER_CHAR` is deleted. `RegexCompiler` gains a memory budget next to its work
   budget, so pre-run compiles are bounded in both dimensions.
3. **I1 pinned by tests that fail without it** (m1): a unit row that refuses mid-build, and a VM
   row for a guest string pattern under a small heap.
4. **m2:** the adapter's `matchAll` reads `lastIndex` when called, not when first iterated.

**What this does not fix, and why that is accepted:** regex remains a large surface, deprecated
in AJS (`docs/pattern.md`). The structural answer is Pattern, where one engine step is one
charge. This plan closes the surface for 0.14; it does not make regex the long-term tool.
