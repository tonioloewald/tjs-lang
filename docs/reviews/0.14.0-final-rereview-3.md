## Blockers

### B-1: Non-numeric or NaN `fuel` turns the admission budget into NaN, so the argument walk fails open *(verified; security and correctness merged)*
`src/vm/vm.ts:212, 293–296`

- **Cause:** `startFuel = options.fuel ?? 1000` is never validated. `argsBudget = Math.min(argsCap, startFuel * ARG_BYTES_PER_FUEL)` comes out NaN, and every `bytes > budget` check is then false.
- **Measured:** a 5M-element argument is refused in 13ms at fuel 100. At fuel `'abc'` it takes 1455ms, at NaN 1830ms and at `{}` 1618ms, and all three end in 'Out of Fuel'. Through Eval: 138ms at fuel 1000 against 1.5–1.9s at `'abc'` or `{}`.
- **Reach:** in `functions/src/index.tjs`, the callable (~124) and the HTTP POST (~232) check only `fuel > 10000`, and `'abc'` passes that check. Any signed-in caller can reach it. `fuelUsed` comes back NaN, which is logged as `|| 0`, so the work is also unbilled.
- **Fix:** in vm.run, before admission, refuse unless `typeof fuel === 'number' && !Number.isNaN(fuel) && fuel >= 0` (Infinity stays legal). Make `membraneValue` treat a non-numeric or NaN `maxBytes` as 0. Validate `typeof fuel === 'number' && Number.isFinite(fuel) && fuel > 0` in both endpoints. Add a test that `'abc'`, NaN and `{}` with a 5M-element argument are refused in under 100ms.

### B-2: The admission rate is uncalibrated. At fuel 10000 a 10MB argument is admitted and costs about 2.1–2.5s before 'Out of Fuel' *(verified; security)*
`src/vm/vm.ts:68, 294–317`

- **Measured:** `vm.run(ast, { items: Array(5e6).fill(1) }, { fuel })` takes 17ms at fuel 100, 126ms at fuel 1000 and 2472ms at fuel 10000. Ten thousand fuel of ordinary loop execution takes about 20ms, so `ARG_BYTES_PER_FUEL = 8000` buys roughly 100 times more CPU per fuel unit than execution does. The data is also charged twice: once at admission and again at the varsImport heap walk.
- **Reach:** `run` and `agentRun` accept fuel up to 10000 from any signed-in account. Public `page` functions are also exposed wherever their author set a high fuel. This is the same roughly 2.4s pre-budget cost as the previous B-1, now reached at fuel 10000 instead of 1000. The existing "refused CHEAPLY" test runs only at fuel 100, so it cannot see this.
- **Fix:** price admission by measured CPU. Lower `ARG_BYTES_PER_FUEL` and/or lower `DEFAULT_ARGS_MAX_BYTES` to the ~4MB order of `membraneMaxBytes`, and add a fast path for dense primitive and JSON-shaped data. Stop the double charge. Add a hostile-size test at fuel 10000 that asserts a wall-clock or fuel-per-ms bound. **Fix this together with the cap-bound minor below; they share the budget arithmetic.**
- **Re-review scope (B-1 + B-2):** security + efficiency + correctness over the vm.ts admission prologue, `membraneValue` budget handling, and every entry path (Eval, SafeFunction, vm.run, AstVM, nested agentRun/runCode, and both functions endpoints).

## Majors (verified; fix before final)

### M-1: `runCode` transpiles guest-built source with no size cap at a flat cost of 1; neither fuel nor timeout bounds it *(verified; security; predates this diff)*
`src/vm/runtime.ts:~4252–4318` (the sibling `transpileCode` atom has the same shape)

- **Measured:** about 220KB of guest-built source at timeoutMs 500 takes 1167ms and is charged about 61 fuel. 500KB takes 6.6s and is charged 160 fuel.
- **Reach:** hosts that grant `code.transpile`, which is the documented way to enable agent-written code. The functions/ endpoints do not grant it.
- **Fix:** refuse source over `DEFAULT_MAX_SOURCE_BYTES` (or a ctx option) before transpiling, and charge per byte first, as jsonParse does with `chargeForSize`. Either apply the same gate to vm.run's string-source path or document that path as trusted-only (that claim is unverified). Add a test that a 500KB source is refused in a few milliseconds.
- "Predates this diff" is not a reason to defer. It is the named class, so it belongs in the same entry-phase fix.

### M-2: The attestation vouches for the tested tree, not for the locally built dist/. npm ships a CI rebuild that the suite never ran against *(verified; blast-radius; lowered from blocker to major; **unmet owner requirement**)*
`.github/workflows/publish.yml:147–164`, `tosijs-coding-practices/tools/attest.ts:38–45, 82–84, 134–140`

- **The gap:** dist/ is gitignored and makes up most of the tarball. The attestation records only `HEAD^{tree}`, the commit, the Bun version and the lane results. publish.yml runs `bun run make` on ubuntu and packs *that* dist/. The "build reproduces every shipped tracked file" check cannot see dist/, and `test:release` checks dist/ paths, not contents. The old `.release-gate` dist/ hash (`release-stamp.ts`) lives in `prepublishOnly`, and `npm stage publish <tarball>` never runs `prepublishOnly`, so on this path that protection is gone.
- **Why this matters now:** the owner asked specifically for a vouchsafe of a **locally generated build**. The current flow vouches for a source tree and ships a different build. The Bun pin reduces the risk but does not check it, and the workflow's own comment records the same lockfile producing a different `dist/iife.js`.
- **Fix, upstream in tosijs-coding-practices so every adopter gets it (keep the template byte-identical):** `attest.ts` records a per-file sha256 manifest of what would ship (the `npm pack --dry-run --json` file list, or at least dist/), taken after `make` on the clean tree. Then either (a) CI recomputes the manifest after its own build and fails on any mismatch, or (b) the locally built, attested tarball or dist/ is itself what gets staged. Option (b) matches the owner's wording most directly. Neither option runs the suite in GitHub. Use per-file hashes, not npm tarball integrity, because file modes differ between macOS and Linux.
- **Re-review scope:** correctness + blast-radius over the attest.ts, release-doctor and publish.yml template remediation, and tjs-lang's re-adoption (template byte-identity).
