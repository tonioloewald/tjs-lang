## Minor

1. **(unverified) correctness: the entry repeats `overloads[0]` for groups with no implementation.** `src/lang/emitters/from-ts.ts:~3159`
   - **What happens:** for `declare class D { m(a: string): string; m(a: number): number }`, the output is `methods.m = { params:{a:string}, returns:string, overloads:[{a:string→string},{a:number→number}] }`.
   - **Why it matters:** the commit and CHANGELOG say methods now use the top-level-function shape, where the entry is the implementation and `overloads` holds only the signatures. A consumer that renders "entry plus overloads" will show `m(a: string)` twice for every abstract or ambient overload set.
   - **Separate, older gap:** ambient top-level functions (`declare function f(...)` ×2) still keep only the last signature and record no `overloads` at all. So there is currently no single shape for groups with no implementation.
   - **Fix:** choose one rule and document it on `FunctionTypeInfo.overloads`. Either:
     - (a) the entry is signature 0 and `overloads` holds the rest, or
     - (b) `overloads` is the full list and the entry is only a summary.

     Then pin the rule with a `declare class` row in `from-ts-class-metadata.test.ts`. The ambient branch is currently tested only through `abstract`.

2. **(unverified) blast-radius: constructor overloads still keep only the last signature.** `src/lang/emitters/from-ts.ts:~3073`
   - **What happens:** `class A { constructor(a: string); constructor(a: number); constructor(a: any) {} }` gives `classes.A.constructor.params.a` = `any`.
   - **Why:** `constructorInfo` is reassigned for every `ConstructorDeclaration`. It is the same defect the commit fixed for methods, still present at the other site that has it.
   - **What is on record:**
     - The CHANGELOG says "method OVERLOAD signatures", which is literally accurate, but a reader will assume constructors are covered too.
     - TODO.md has no entry for this. I checked: the new "Carry type-only class facts" section covers abstract members and class fields, not constructors.
   - **Fix:** either
     - group constructor declarations the same way as methods (implementation plus an optional `overloads`), or
     - file it in TODO.md and add "(constructors not yet)" to the CHANGELOG entry.

## Nit

3. **(unverified) blast-radius: for a group with no implementation, the entry changed from the last signature to the first.** `src/lang/emitters/from-ts.ts:~3160`
   - Before this commit, `declare class D { m(string); m(number) }` gave `methods.m.params.a` = `number`. It now gives `string`.
   - A consumer that reads only the entry will see the type silently change.
   - First signature wins, which matches TS declaration order, so keep it and say so in the CHANGELOG.
   - This depends on the rule chosen in item 1, so fix the two together.
