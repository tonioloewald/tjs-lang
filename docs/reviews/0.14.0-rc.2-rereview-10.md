### M1. AJS helper functions each get their own RegexCompiler, so the per-source compile budget is bypassed (confirmed, correctness)

**Where:**
- `src/lang/emitters/ast.ts:1466`: the helper context literal sets neither `parent` nor `regexCompiler`.
- `ast.ts:503-507`: `regexNode` walks `ctx.parent` to the root and does `root.regexCompiler ??= new RegexCompiler(ctx.source.length)`.

**Failure:**
- Every helper body becomes its own root, with a full budget of 200 × the whole source length and an empty cache.
- Inline in `main`, N copies of `/(?:(?:){10000}){k+i}/` are refused in 3-10ms ("too large to compile").
- One literal in each of N helpers called from `main` transpiles ok:

  | Helpers | Source size | Result | Time |
  |---|---|---|---|
  | 20 | 1.5KB | ok | 76ms |
  | 80 | 5.9KB | ok | 700ms |
  | 4 literals per helper | 37KB | ok | 3.7s |

- The total grows with helpers × source length, about 7,500 work per byte against the intended 200 per byte.
- The new vm-budgets M2 rows cover only the single-function path, so they stay green.

**Fix:**
1. Create the RegexCompiler once, when the root TransformContext is built (`ast.ts:244`).
2. Pass it explicitly to `helperCtx`, or hang it on a structure the helpers already share (`helpers`).
3. Drop the lazy `??=` root walk, so a context without a compiler is a bug rather than a fresh budget.
4. Add a vm-budgets row with N helpers, each holding distinct costly literals, that must throw `/too large to compile/` promptly.
5. Grep for any other context literal built without `parent`.

**Re-review scope:** correctness over `emitters/ast.ts` context construction and the new row.

### TODO.md (Virta board, `--project tjs-lang`): correctness / blast-radius lenses

- [ ] **Charge regex program bytes before building them, and at both creation sites (confirmed minor, correctness).**
  - Where: `src/vm/runtime.ts:3911-3931` and `src/vm/string-methods.ts:45-47`.
  - The `'regex'` expression compiles the whole program before it calls `allocate(regexBytes)`. For `/a{10000}/` that is 1,560,288 bytes built under a 256KB ceiling before the refusal. The overshoot is bounded by MAX_REGEX_PROGRAM, but it still breaks I1 ("nothing allocates before it is charged").
  - `prepare()` for a string pattern (`s.search('a{10000}')`) charges `threadBytes` only and never `regexBytes`, so the two creation paths disagree.
  - Fix: charge a pre-bound through compileRegex's charge callback as instructions are emitted, and charge `regexBytes` in `prepare()` too. At minimum, document the bounded overshoot beside I1 in `docs/vm-budgets.md`.
- [ ] **CHANGELOG: record the consumer-visible effects of `fix(vm)!` 381a5fc (confirmed, downgraded to nit, blast-radius).**
  - Add under the "Since rc.1" regex paragraph:
    - A compiled regex is charged its program size against `maxHeapBytes`, both when it is created and while it is held.
    - Regex literals in one source share a compile budget of max(50k, 200 × source bytes), and an over-budget source is refused with "The regexes in this source are too large to compile".
    - `__fuel` and `__rx` are reserved identifiers in predicates.
  - Then run `bun run docs` so `demo/docs-fresh` stays green.
  - Cheap. Do it with the M1 fix.
- [ ] **(unverified) The predicate adapter's `Symbol.matchAll` ignores `lastIndex`.**
  - Where: `src/lang/predicate-regex.ts:114`.
  - Reported: with `/a/g` and `lastIndex = 2`, the adapter gives [4,2] where native gives [2,2]. If true, a `$predicate` can disagree with the same source run natively, which contradicts the new "lastIndex (global and sticky semantics)" doc claim.
  - Fix: `allMatches` takes a start offset, and `[Symbol.matchAll]` passes `ToLength(this.lastIndex)`. Or narrow the doc. Add a differential row to `redos-lint.test.ts` round 5.
- [ ] **(unverified) Verify-then-compile callers compile each predicate literal twice against two per-source budgets.**
  - Merges the correctness nit and the blast-radius nit.

  - These call `verifyPredicate(src)` and then `compilePredicate(src)`, so each builds its own RegexCompiler. That gives about 2× the setup cost, and the `$predicate`-as-data path does not get the single-budget guarantee that the `verifyWith` fix promised. It is linear, so not a DoS.
  - Fix: expose a variant that returns the verify result together with the compiled module from one RegexCompiler, or take the entry name from compilePredicate's own verification.
